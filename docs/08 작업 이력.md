  였다면 여기서부터 구현 문서 → [[22 설치판 아키텍처]] · [[23 설치판 구현 계획]]
- 구조 핵심
  - **디스크 3영역 분리** (프로그램 / 사용자 데이터 / 볼트). 업데이트가 사용자
    데이터를 못 건드리게 하는 장치. `.research-agent/`(sqlite·충돌본)를 **볼트 안**에
    둬 볼트 폴더 하나만 복사하면 이력·감시까지 이전됨
  - **Program Files에 설치하지 않는다** — 거기 쓰려면 관리자 권한이 필요해
    **자동 업데이트마다 UAC가 뜬다**. per-user 설치(`PrivilegesRequired=lowest`)
  - **경계 셋**(`store`·`keys`·`packs`)만으로 두 에디션이 갈린다. 이걸 넘는 분기는 반려
  - `LocalStore` 는 현행 `store.py` **인터페이스를 그대로** 유지 → 호출부 18곳이 거의 무변경
  - 신규 고려 2건: 볼트 전수 읽기가 화면당 여러 번 일어나므로 **mtime 증분 캐시** 필요
    (Supabase일 땐 REST 1회였음) · 앱과 작업 스케줄러가 같은 sqlite를 열므로 **WAL 필수**
  - **원자적 쓰기 + mtime 충돌 감지** — Obsidian이 연 파일을 반쪽으로 읽거나
    사용자 편집을 덮어쓰는 사고를 둘 다 막음. 자동 병합은 하지 않음(판정은 사람)
  - **상태별 잠금 표**를 미리 확정 — 어떤 실패에도 **볼트 열람·내보내기는 안 막는다**
    (고객 데이터를 인질로 잡지 않는다). 활성화 서버 장애는 **유예 처리**
  - **네트워크 아웃바운드 전표** 작성 — 보안 검토에 그대로 제출 가능. 이 표에 없는
    아웃바운드가 생기면 리뷰 반려
- 계획 핵심
  - **0단계 패키징 스파이크(1주)가 선행 필수** — 유일하게 실측이 없는 미지수.
    한글 사용자명 경로·국내 백신 통과까지 포함. 실패해도 배포 형태만 바뀌고 1~7단계 무영향
  - **프롬프트 팩 분리(2단계)를 라이선스보다 먼저.** 나중에 하면 전 모듈을 다시 헤집는다.
    조립 함수는 두고 **문자열 리터럴만** 치환하며, DoD에 **분리 전후 프롬프트
    바이트 단위 동일** 비교를 넣어 회귀를 막는다
  - **판매 최소선은 0~7단계.** 8단계(모니터링 로컬 스케줄)는 없어도 판매 가능
  - 상시 회귀 6종(R1~R6) — 특히 **R1 체험판 정상 기동**: 영업 도구가 죽으면 안 되므로
    Supabase 경로를 지우지 않는다. 이 작업은 교체가 아니라 **분기 추가**
- 아직 코드 변경 없음. 다음 행동은 **0단계 스파이크**

### 32. 설치판 0단계 — 패키징 스파이크 실측 (첫 코드 산출물)

- **결론: 임베디드 파이썬 방식 확정.** 배포 형태를 바꿀 이유 없음 → [[23 설치판 구현 계획]]
- 산출물 `packaging/` — `build.ps1` · `launcher.py` · `installer.iss` · `app.ico` · `VERSION`
- 실측: **설치 파일 73MB** · 설치 62초 · 디스크 377MB(다이어트 전 533MB) ·
  **첫 기동 3.1초** / 2회차 1.9초
- 라이트 조사 1건 e2e 성공(Gemini), 보고서 3종 생성, 한글 경로 정상,
  `pages/` 3개 등록 확인(26번 판별법), **Supabase 없이도 기능 저하 없음**
- **시스템 파이썬 격리 확인** — `sys.path` 3개가 전부 런타임 내부.
  파이썬 없는 PC에서 도는 것의 직접 증거
- 함정 7건 (상세는 설계서 23)
  - **MAX_PATH(260자)로 빌드가 실패**했다 — 롱패스 꺼진 기본 상태 + 긴 작업 경로.
    실제 설치 위치 기준으로는 199자로 여유 61자 → 설치 경로를 더 깊게 만들지 않는다
  - **`.ps1` 을 UTF-8 BOM으로 저장해야 한다** — 5.1이 BOM 없으면 ANSI로 읽어 한글
    주석이 깨지고 구문 오류. [[11 원커맨드 배포]]의 한글 이슈가 빌드 스크립트에서 재발
  - `google-api-python-client` **98MB(전체의 18%)** 제거 — Google Slides 엔진 전용이고
    그 엔진은 ImportError를 잡아 안내를 내므로 기능 저하 없음
  - **빌드가 `.streamlit/` 를 통째로 복사하면 로컬 `secrets.toml` 이 고객 PC로 나간다**
    → `config.toml` 만 담고, 산출물 비밀 파일·키 패턴 스캔을 빌드 실패로 연결
  - 그 스캔 첫 판이 `certifi\cacert.pem` 을 오탐 → 검사 범위를 앱 영역으로 한정
  - **런처 exe를 컴파일하지 않기로 결정** — 바로가기가 `pythonw.exe`로 `launcher.py`를
    부르고 아이콘만 씌운다. 컴파일 산출물이 없으면 백신 오탐 여지가 준다
  - **설치 후처리로 바이트코드를 선컴파일한다** — 없으면 진짜 첫 실행이 **10.1초**.
    `compileall -j 0` 15초를 쓰면 3.1초로 떨어지고, `.pyc` 는 설치 시 생성되므로
    **다운로드 용량은 그대로 73MB**. 측정 함정도 함께 기록: 빌드 직후 스모크 테스트를
    돌리면 캐시가 덥혀져 "4.3초"로 잘못 보인다 — **콜드스타트는 갓 설치한 상태에서 잰다**
- 인스톨러(Inno Setup 6.7.3, 사용자 승인 후 `/CURRENTUSER` 설치)까지 실측 완료
  - 무인 설치·제거 종료 코드 0, 시작 메뉴 바로가기, Edge 앱 모드 창 정상
  - **제거 후 프로그램은 완전 삭제되고 볼트·`agent.db`·`config.json` 은 남는다** —
    [[22 설치판 아키텍처]] 2절 3영역 분리가 의도대로 동작
  - Windows Defender 검사 위협 없음. **국내 백신(알약·V3)은 미검증** — 배포 전 확인 필요
  - `dist/` 를 `.gitignore` 에 추가 (73MB 인스톨러가 저장소에 들어갈 뻔했다)

### 34. 설치판 2단계 — 프롬프트 팩 분리 (문구를 코드 밖으로)

- **골든 스냅샷을 먼저 뜨고 분리했다.** `tests/prompt_golden.py` 가 고정 입력으로
  프롬프트·스키마·구성표 **62항목**을 만들어 저장하고 분리 후 바이트 단위로 비교한다.
  LLM을 안 부르므로 빠르고 결정적. **이 순서가 아니었으면 "비슷해 보이는데 다른"
  프롬프트를 못 잡았다**
- 옮긴 것: `pipeline`(조사·토론·채점·종합 프롬프트, 분량 계획 문구, 채점 기준 9종,
  보고서 스키마) · `ontology`(추출 프롬프트·스키마, 타입 6종, 술어 12종, 축적 지식
  지시문) · `librarian`(시스템·답변 프롬프트·스키마) · `watch`(검색·정리·다이제스트,
  스키마 2종) · `light`(업무 템플릿 5종, 구조화 프롬프트)
  → `core/prompts/pack.json` (prompts 32 · schemas 5 · config 8), 접근은 `core/packs.py`
- 설계 판단 셋
  - **치환자는 `string.Template`(`$name`)** — 프롬프트에 JSON 스키마 예시 같은
    중괄호가 섞이므로 `str.format` 은 위험. 본문에 `$` 가 없음을 먼저 확인했다.
    `safe_substitute` 가 아니라 `substitute` — 못 채운 치환자가 조용히 남지 않고 터진다
  - **임포트 시점에 팩을 읽지 않는다** — 팩이 없어도 앱은 뜨고 볼트 열람은 계속돼야
    하므로. PEP 562 모듈 `__getattr__` 로 접근 순간에 꺼낸다(프록시가 아니라 진짜
    dict/list 라 SDK 에 그대로 넘어간다). 대신 호출부를
    `from core import pipeline` + `pipeline.REPORT_SCHEMA` 로 바꿨다
  - **조립 로직은 코드에 남겼다** — 팩은 문구를, 코드는 어디에 끼울지를 안다.
    분량 계획도 개수 산식은 코드, 서술 문구는 팩으로 갈랐다
- 검증: 골든 **62항목 달라짐 0** · Gemini 라이트 실조사 e2e 성공(섹션 3·표 1·출처 2) ·
  **팩 제거 시 볼트 쓰기/읽기는 그대로 동작**하고 안내 문구 있는 PackError ·
  1단계 테스트 36항목 재통과
- 부수 효과: **앱 재배포 없이 프롬프트를 갱신**할 수 있게 됐다 — ESG 규제가 매년
  바뀌는 도메인에서 라이선스와 무관하게도 값이 있다

### 35. 설치판 3단계 — 키·설정 화면 (OS 키체인)

- 산출물: `core/keys.py` · `pages/0_⚙️_설정.py` · `providers.verify_key()` ·
  프로바이더 3사 생성자 `api_key` 인자 · `config.api_key_for()`
- **SDK 가 환경변수를 암묵적으로 읽게 두지 않는다** — `api_key_for()` 로 꺼내

- **키체인 백엔드가 없으면 조용히 환경변수로 폴백** — 체험판(리눅스 헤드리스)에는
  백엔드가 없으므로 같은 코드가 두 에디션에서 다 돌려면 필수.
  `keyring.backends.fail.Keyring` 인지 확인해 "있는 척하는 백엔드"를 걸러낸다
- 온보딩은 **Gemini 먼저** (무료 티어 → 카드 없이 시작, 라이트 모드라 키 하나로 전 기능)
- 검증(패키지 런타임): 키체인 왕복·**os.environ 무오염** · **키 없이 띄운 앱이
  외부 등록 키를 재시작 없이 인식** · 잘못된 키 즉시 400 반환 · 프로바이더별 독립
- **실측으로 잡은 버그 2건**
  - **`version.json` BOM** — PowerShell `Out-File -Encoding utf8` 이 BOM을 붙여
    `json.loads` 가 조용히 실패, **버전이 늘 `dev`** 였다. 설정 화면에 "버전 dev"가
    떠서 발견. 표시만의 문제가 아니라 **6단계 자동 업데이트의 버전 비교가 통째로
    망가지는** 버그였다. 읽는 쪽 `utf-8-sig` + 굽는 쪽 BOM 제거로 양쪽 수정
  - **2단계에서 흘린 `ontology._norm` 유실** — 팩 분리 때 리터럴 블록과 함께 삭제됨.
    골든 테스트는 프롬프트만 보므로 못 잡았고, 주입 실패를 안전장치가 삼켜
    **조사는 성공한 채 지식만 조용히 주입 안 되는** 상태였다.
    2단계 이전 커밋과 최상위 정의 목록을 기계 비교해 유실 범위 확정(그것 하나뿐),
    재발 방지로 `tests/test_core_smoke.py` **26항목** 신설 —
    LLM 없는 순수 로직(병합·인덱스·주입 매칭·검토 필요 반영·사서 검색·감시 지문·
    zip 왕복)을 전부 실행한다. 골든 테스트의 사각지대가 정확히 거기였다

### 38. 설치판 6단계 — 자동 업데이트 (패치가 고객 PC 까지)

- 목표: 패치가 고객 PC 까지 간다 (→ [[23 설치판 구현 계획]] 6단계 · [[19 두 제품 구성과 자동 업데이트]] 4절)

- **로컬 릴리스 서버를 세워 0.1.0 → 0.2.0 전 과정을 실제로 돌렸다.**
  사이드바 알림 → 매니페스트 재조회 → 176KB 델타 → sha256 검증 → 앱 종료 →
  `app`↔`app.bak` → 전개 → 재시작 → 헬스 자가진단 → 백업 삭제.
  볼트 35노트·`agent.db`·설정 표식 모두 그대로
- **실측으로 잡은 버그 5건** (단위 시험으로는 안 잡히는 것들)
  1. **업데이터가 자기 자신을 죽였다** — `taskkill /T` 는 트리를 죽이는데
     업데이터가 앱의 자식이었다. `/T` 제거 + `cmd /c start` 로 트리 밖에서 기동.
     ⚠️ **5단계 재시작 버튼에도 같은 결함이 있었다** — 그때는 PowerShell 로만
     눌러 봐서 드러나지 않았다
  2. **업데이터의 cwd 가 `app\`** 이었다(서버 cwd 를 물려받음). 자기가 선 폴더는
     이름을 못 바꾼다 — 프로세스를 다 죽여도 `WinError 32` 가 안 사라지던 원인
  3. **캐시된 판정으로 내려받아** 낡은 sha256 이 "위변조" 헛경보를 냈다 →
     적용 직전에는 매니페스트를 다시 받는다. 반대 방향(낡은 해시가 맞아떨어져
     옛 버전을 새 버전으로 믿는 것)이 더 위험하다
  4. **델타가 버전 파일을 못 갈아 끼웠다** — `version.json` 이 설치 루트에만 있어
     같은 업데이트를 영원히 다시 권했다 → `app\` 안에도 두고 그쪽 우선
  5. **판정 캐시가 업데이트 직후에도 "새 버전 있음"** → 판정 대신 매니페스트를
     캐시하고 읽을 때마다 다시 판정
- 안전 규칙: https 만 · sha256 필수(틀리면 파일도 삭제) · 전개 전 zip 전수 검사
  (zip-slip·`app.py` 없으면 거부) · 중단 시 런처가 첫 기동에서 자동 복구 ·
  **조사 중에는 재시작 금지**(파일 표식, `finally` 로 반드시 해제, 6시간 뒤 만료)
- 검증: 0.1.0→0.2.0 실제 업데이트 · sha256 불일치 거부 · **교체 중단 상태를
  인위로 만들어 자동 복구 확인** · 볼트/설정 보존 · R1 체험판 무회귀
- 회귀 6종: 골든 62 · LocalStore 36 · 스모크 26 · 볼트 69 · 휴대폰 37 · 업데이트 60

### 41. 배포 준비 ① 라이선스 서버 — 배포 전에 서명 호환성을 못 박다

- 요청: 남은 배포 항목을 1번부터 순서대로 (1 라이선스 서버 · 2 릴리스 파이프라인 ·

  그래서 **코드로 할 수 있는 것을 전부 끝내고 절차서를 만들었다** ([[24 라이선스 서버 배포]])
- **가장 위험한 이음매를 배포 전에 검증했다.** 서버(Deno)와 클라이언트(파이썬)의
  서명이 어긋나면 증상은 "모든 고객의 활성화 실패"인데, 서버를 켜기 전에는
  드러나지 않는다.
  - 서명 로직을 `supabase/functions/license/sign.ts` 로 분리 (Deno 전용 API 미사용)
  - `tests/test_edge_signature.py` 가 **실제 sign.ts 를 Node 로 불러** 서명을 만들고
    파이썬 클라이언트로 검증 — 실제 팩 16KB·한글·이모지·제어문자까지 통과
  - 기기 지문/만료/팩을 한 바이트만 바꿔도 검증이 실패하는 것까지 고정
- **설계 변경 1건 — 팩을 환경변수에서 스토리지로.** 프롬프트+시드를 합치면 48KB라
  시크릿에 담기 부담스럽고, 무엇보다 **팩을 갈 때마다 함수를 재배포**해야 했다.

### 46. 첫 설치 파일 — 굽고, 깔고, 활성화까지

설치 파일이 한 번도 만들어진 적이 없었다. 만들어 보니 **네 군데가 깨져 있었다.**
전부 "개발 PC 에서는 멀쩡하고 설치본에서만 드러나는" 종류다.

| 무엇 | 증상 | 왜 안 보였나 |
|---|---|---|
| `vault_seed` 무조건 복사 | 빌드가 멈춤 | 44번에서 팩을 뺄 때 빌드 스크립트를 안 고쳤다 |
| 인스톨러를 `packaging\dist` 에서 찾음 | 컴파일 성공 → **매니페스트에서 조용히 누락** | 실패가 아니라 "없음"으로 처리됐다 |
| `[InstallDelete]` 없음 | 덮어 설치가 옛 파일을 남김 | 새 설치만 해 봤다 |
| 최상위 `ui_*.py` 넷 누락 | 첫 화면에서 `ModuleNotFoundError` | 복사 목록을 손으로 나열했다 |

셋째가 가장 무겁다. 시연용 빌드(`-IncludePack`)를 깔았던 PC 를 정식판으로
올리면 **옛 팩이 남아 라이선스 검사를 영원히 통과한다.** 실제로 이 PC 에서
8/9~8/10 자 팩과 시드가 그대로 살아남는 것을 확인했다. 델타 업데이트
(`updater.py`)는 `app` 을 `app.bak` 으로 밀어내므로 원래 안전했다 — 인스톨러만
그렇지 않았다.

넷째는 고치는 것보다 **다시 안 생기게 하는 것**이 중요했다. 이름을 손으로
나열하는 한 화면을 추가할 때마다 같은 사고가 난다. 최상위 `*.py` 를 전부 담게
하고, **구운 런타임으로 구운 앱을 실제로 import 해 보는 기동 검사**를 빌드에
넣었다. 파일이 빠졌는지 눈으로 세는 대신 파이썬에게 묻는다.

**설치 → 활성화 한 바퀴 통과.** 이 PC 에는 개발 저장소와 팩 원본이 그대로
있는데도 설치본이 거부했다(개발용 폴백 차단이 실제로 돈다). 키를 넣으니
서버에서 팩이 내려와 서명을 통과했다 — `활성화됨 · 좌석 1/2 · 구성요소 0.1.0`.
재설치해도 라이선스가 남는 것까지 확인했다(설정은 `{app}` 밖에 있다).

**문구 하나 고침**: 팩이 없을 때 "없음 (재설치 필요)" 라고 적혀 있었다. 팩은

믿고 다시 깔면 같은 화면으로 돌아온다. "활성화가 필요합니다" 로 바꿨다.

**남은 것**: 업데이트 확인이 404 다 (`latest.json` 미배포 — 릴리스를 내면
풀린다). 백신(알약·V3) 반응과 서명 없는 exe 의 SmartScreen 경고는 **미검증**.
고객 다운로드 경로(홈페이지 `/download/`)도 아직 없다.

### 47. 볼트 스냅샷 캐시를 껐다 켜도 남게

지식 비서가 볼트를 어떻게 읽는지 묻는 질문에서 나왔다. 재 보니 **기동마다
볼트를 전수 재독**하고 있었다 — mtime 증분 캐시는 있었지만 메모리에만 있었다.

| 노트 수 | 전 (매 기동) | 후 (2차 기동) | 1개 수정 후 |
|---:|---:|---:|---:|
| 500 | 4.0초 | **21ms** | 31ms |
| 2,000 | 12.9초 | **75ms** | 82ms |
| 10,000 | 71초 | **359ms** | 371ms |

`agent.db` 에 `vault_cache` 표를 두고 mtime+size 가 같으면 파일을 열지 않는다.
**버려도 되는 표다** — 원본은 언제나 볼트의 `.md` 파일이고, 지우면 느려질 뿐
잃지 않는다(시험에 그 항목을 넣었다). 캐시를 못 읽는 것은 볼트를 못 여는
이유가 아니므로 뒷단 실패는 전부 삼킨다.

노트는 조사할 때마다 늘기만 하므로 이 지연은 **조용히 자란다.** 처음엔 1초라
아무도 모르고, 반년 뒤 "요즘 느리다"로 나타나며 그때는 원인을 짚기 어렵다.

**토큰은 원래 문제가 아니었다.** 근거 노트 8개·노트당 6,000자·전체 30,000자
상한이 걸려 있어, 볼트가 100개든 10,000개든 LLM 에 가는 양은 3,353자로 같다.
어휘 검색도 10,000개에서 216ms 다. 커지는 것은 **디스크 읽기 하나뿐**이었다.

**규모 예상을 바로잡았다.** 처음에 "반년이면 2,000개"라고 했는데 엔티티가
겹치는 것을 빼먹은 계산이었다. CBAM 을 열 번 조사해도 `EU CBAM.md` 는 한 장이다.
실제로는 **1년에 300~500개**다.

함께: 업데이트 확인 간격을 6시간 → **하루 한 번**으로 (사용자 요청). 급한 건은
`critical`·`min_supported` 가 따로 다루고, '지금 확인'은 간격을 건너뛴다.

회귀 10종 통과.

### 48. 첫 고객의 리서치를 감시가 감당할 수 있는가

고객사가 원하는 것이 표로 왔다 — **6개 범주 × 7개 사이트**, 범주마다 확장
키워드가 붙은 것. 그 표를 놓고 감시 기능을 하나씩 대 보니 다섯 군데가 모자랐다.

| 모자란 것 | 왜 문제인가 |
|---|---|
| '일' 주기가 없음 | 시각만 있어 **매일 도는 것 말고 선택지가 없었다** |
| 첫 장만 읽음 | 범주가 섞인 목록은 관심 항목이 다음 장으로 밀린다 |
| 알림 상한이 고정 | 뉴스 매체(하루 20건)와 공지 게시판(주 1건)이 같은 값을 썼다 |
| 제목 필터가 없음 | 회계기준원 1,927장 = 19,270건을 전부 요약할 수는 없다 |
| 중요도 척도가 없음 | "8점"이 무슨 뜻인지 아무도 정의한 적이 없었다 |

**"첫 장이면 충분하다"는 내 가정을 고객이 틀렸다고 했다.** 최신순 목록이라도
종류가 다양하면 첫 장에 다 못 올라온다는 것이다. 맞는 지적이라 **넘길 범위를
날짜가 정하게** 했다 — 주 1회 감시면 일주일치를 다 가져와야 하고, 그 장에서
가장 새 날짜가 기준일보다 오래되면 그 아래는 볼 필요가 없다. 상한(10장)은
마지막 안전장치로 남긴다.

그 과정에서 **감지 자체가 고장 나 있던 것**이 드러났다. 본문을 뽑을 때
`get_text(separator="\n")` 의 결과를 다시 공백으로 이어 붙이고 있었다 —
페이지가 통째로 한 줄이 된다. 줄 집합으로 비교하는 `_added_lines` 는 그러면
**전부 아니면 전무**가 되어, 조회수 하나만 바뀌어도 페이지 전체가 '새 줄'이
되고 요약 LLM 은 메뉴까지 뒤섞인 5천 자를 받는다. 6개 사이트를 두 바퀴씩
돌려 보고서야 보였다.

**중요도는 구간(7~8)이 아니라 1~5 낱값으로.** 구간을 쓰면 7과 8의 차이가
여전히 정의되지 않는다 — 없애려던 빈칸이 그대로 남는다. 다섯 줄의 뜻은
**고객이 고친다**: 규제 감시와 경쟁사 동향 감시가 같은 잣대를 쓸 이유가 없다.
줄 수는 다섯으로 고정한다 (일곱 줄을 적으면 스키마도 정렬도 어긋난다).

낱말을 정해 두면 **걸린 줄 하나가 항목 하나**가 된다. 뭉뚱그린 "본문 변경
(535자 추가)"는 알림 제목으로 쓸모가 없다 — 열어 보기 전에는 무슨 일인지
알 수 없다.

### 49. 원문까지 읽기 · 과거 자료 적재

감시는 목록 한 장을 읽으므로 쌓이는 것은 **제목과 링크뿐**이다. 그것만으로는
지식볼트라기보다 링크 모음이다. 두 기능이 그 사이를 메운다.

**원문까지 읽기** — 문턱을 넘은 항목의 기사 본문을 열어 제대로 요약한다.
요약을 **두 번 부르는 이유는 순서다**: 단계는 요약이 끝나야 나오는데 원문은
요약 전에 있어야 한다. 1차는 제목만으로(싸다), 2차는 고른 것의 원문을 붙여
**전체를 다시** 요약한다(고른 것만 따로 요약해 기워 붙이면 머리말과 총평이
어긋난다). 문턱·건수·낱말 셋 다 고객이 정한다.

**과거 자료 적재** — 감시가 오늘부터를 쌓는다면 이건 어제까지를 채운다.
성질이 반대다.

    감시                    적재
    ────────────────────────────
    놓치지 않기             바닥 깔기
    매일 반복               한 번
    알림 보냄               **안 보냄**
    건당 요약               **묶음 요약**

19,270건을 세 겹으로 줄인다: 기간(년/월 범위를 사람이 고른다) → 낱말(제목만
보므로 **LLM 을 한 번도 안 부른다**) → 묶음(달별 25건씩 한 번에 요약).
300건이면 LLM 호출 12회다. 수집과 요약 진행을 **sqlite 에 적어 가며** 하므로
앱을 껐다 켜도 이어서 한다 — 몇 시간짜리 작업에서 "어디까지 했더라"는
물어볼 수 없는 질문이다.

**팩 버전이 앱 버전에 묶여 있었다.** `make_pack.py` 가 앱 버전을 팩에 찍고
있어서, 팩을 갈아도 화면의 `구성요소` 숫자가 안 움직였다. 그래서 팩 회전이
**됐는지 안 됐는지 볼 방법이 없었다** — 실제로 성공한 업로드를 실패로 읽었다.
분리한 뒤 `구성요소 0.1.0 → 0.2.0` 이 화면에서 바뀌는 것을 확인했다.

### 50. 알림을 설치판에서도 — 그리고 말이 틀렸던 곳들

정식판에서 알림을 **켤 방법이 아예 없었다.** 이메일·카카오 설정을 환경변수로만
읽었는데 설치판에는 `.env` 가 없다. 3단계에서 API 키를 화면에서 넣게 고쳤을 때
그 이웃을 안 본 것이다 — 같은 종류의 사고가 두 번째다.

윈도우 알림은 모듈 설치 없이 붙였다 (`ToastNotificationManager` + 파워셸
AUMID 빌리기). 이메일은 서비스를 고르면 SMTP 주소·포트가 채워지게 했다.

**말이 틀린 곳이 두 군데 있었고, 둘 다 써 봐야 드러났다.**

- "앱 비밀번호를 발급해 넣으세요" → 신청하면 **메일이 온다**로 읽혔다.
  실제로는 발급 화면에 그 자리에서 16자리가 뜨고 창을 닫으면 다시 못 본다.
- 서비스별 안내를 뭉뚱그려 놔서 Gmail 안내를 보고 **한메일을 등록**했다.
  이제 고른 서비스의 막히는 지점만 나온다 (Gmail 은 2단계 인증, 네이버는
  POP3/IMAP '사용함', 다음은 IMAP/SMTP 켜기…).

시험 발송 성공. **코드는 멀쩡했고 말이 틀렸다.**

함께: 지식볼트 폴더 선택 창이 브라우저 뒤에 숨었다. 안 띄운 폼의 `TopMost` 는
효과가 없고, 대화상자는 **보여지고 활성화된** 주인이 있어야 앞으로 나온다.
z-order 를 열거해 전후를 확인했다.

### 51. 화면의 칸들 — 넘친 쪽은 볼 방법이 없었다

키워드를 여남은 개 넣으면 한 줄짜리 칸을 금방 넘고, 그때부터는 옆으로 밀려
나가 **전체를 볼 방법이 없다.** 고치려면 눈을 감고 화살표를 눌러야 한다.
여러 줄 상자로 바꿨다 — 넘치면 아래로 접히고 모서리를 끌어 키울 수도 있다.

바꾸고 재 보니 **안 커졌다.** `height=96` 을 줬는데 글 상자는 68 이었다.
`height` 는 글 상자가 아니라 **라벨을 포함한 칸 전체**의 높이다. 라벨 몫(28)을
더해 다시 계산했다. 고객이 실제로 넣은 본문 키워드 196자로 확인 — 86px,
넘침 없음.

**과거 적재가 "멈춘 것처럼" 보이던 것**도 두 겹이었다.

- 걸음마다 사람이 눌러야 했다. 400장짜리면 80번 누르라는 뜻이고, 누르는
  사이 화면은 내내 똑같았다. 한 번 누르면 끝까지 가고, 걸음마다
  "12장 읽는 중 · 2026-07-14 까지 내려옴 · 담은 항목 3건"으로 갈아 끼운다.
- **실제로 열 장밖에 못 읽고 있었다.** 적재가 감시의 `page_urls` 를 그대로
  썼는데 거기 `MAX_PAGES=10` 이 있다. 감시에는 맞는 상한이지만 2022년을
  찾으러 수백 장을 내려가야 하는 적재에는 "열 장 읽고 0건"을 뜻한다.
  상한 없는 `page_url()` 을 따로 뒀다 (적재는 400장까지).

0건으로 끝날 때 **이유를 말하게** 했다. 그냥 "완료 — 0건"만 남기면 고객은
프로그램이 고장 났다고 읽는다.

### 52. 껍데기만 읽고 있었다 — 브라우저로 읽기

첫 고객 사이트(ESG Finance Hub)를 재 보니 이랬다.

| 무엇을 | requests | 브라우저 |
|---|---|---|
| 목록 **페이지** (HTML) | 200 — 그런데 **본문 547자** | 3,117자 |
| 목록 **데이터** (`list.json`) | **403** | 정상 |

페이지는 열린다. 다만 **내용을 자바스크립트가 그린다.** 진짜 목록은 별도
요청에 있고(8,581건, 원문 주소까지) 그 요청만 막힌다. 브라우저 헤더를 한
글자까지 맞춰도 403 이었다 — 헤더가 아니라 **접속 방식(TLS 지문)** 을 본다.
헤더로는 못 넘는다.

넘는 길은 하나뿐이다: **진짜 브라우저로 열기.** Playwright 를 들이면 설치본이
150MB 늘지만 그럴 필요가 없었다 — **런처가 이미 Edge 로 앱 창을 띄운다.**
같은 실행 파일에 `--headless --dump-dom` 을 주면 다 그려진 DOM 이 나온다.
새로 깔 것도, CDP·웹소켓·드라이버도 필요 없다.

처음에는 감시마다 켜고 끄게 했고 **기본을 꺼짐으로 뒀다. 그 판단이 틀렸다.**
사용자가 "어떤 사이트든 브라우저를 쓰면 어떠냐"고 물어 다섯 곳을 재 봤다.

    회계기준원        10건 0.5초  |  10건 1.8초
    임팩트온           0건 0.5초  |  20건 3.3초   ← 브라우저라야 잡힌다
    ESG Finance Hub    0건 0.9초  |  10건 7.5초   ← 브라우저라야 잡힌다
    금융위원회        17건 2.4초  |  17건 5.5초
                    ─────────────────────────
                        5.3초        19.1초  (3.6배)

**브라우저가 더 나쁜 경우가 하나도 없었다.** 임팩트온이 0건이던 것도 기본을
꺼 놔서 몰랐다. 그렇다고 늘 켜면 3.6배 느리다 — 그래서 **자동**을 기본으로
했다: 먼저 그냥 읽고, **목록으로 안 보일 때만** 브라우저로 다시 연다.
'목록으로 보인다'는 글자 수가 아니라 **날짜 붙은 항목 수**로 판정한다
(껍데기도 메뉴로 500자는 채운다). 판단은 첫 장에서 한 번만 하고 감시에
적어 둔다 — 안 적으면 날짜 없는 목록에서 매번 두 번씩 읽는다.

자동을 실제로 걸어 보니 네 곳 모두 옳게 골랐다 (합계 13.2초).

### 53. 고객은 걸어 보기 전에는 되는 곳인지 알 수 없었다

사이트마다 되는 것이 다른데, 고객이 그것을 아는 길은 하나뿐이었다 — 감시를
걸고, 하루 기다리고, 0건을 받는 것. 그러고도 **왜** 0건인지는 알 수 없다.
사이트가 조용한 건지, 낱말이 좁은 건지, 목록을 자바스크립트로 그려 아예 못
읽은 건지 구분이 안 된다. **셋은 대응책이 전혀 다르다.**

🔬 진단 단추가 네 가지를 **재 본다**: 읽히는가 / 항목이 잡히는가 / 날짜가
읽히는가 / **쪽이 넘어가는가**. 넷째가 핵심이다 — 주소에 쪽 번호를 붙일 수
있다고 넘어가는 게 아니다. 무시하고 늘 같은 첫 장을 주는 사이트가 흔하고,
그걸 모르고 적재를 돌리면 같은 열 건을 수백 번 담는다. 그래서 붙여 보고,
2쪽을 **실제로 받아 와**, 1쪽과 비교한다.

만들면서 **내가 두 번 틀렸고 둘 다 실측이 잡았다.**

- 메뉴 열네 줄을 '항목 14건'으로 세고 ESG Finance Hub 에 "잘 읽힙니다"라고
  답했다. 껍데기도 줄은 나온다 — 가르는 것은 **날짜**다.
- 쿼리가 없는 주소에 쪽 번호를 '바꿔 넣기'만 해서, 아무것도 안 붙은 주소로
  시험하고 "안 넘어간다"고 답했다. 회계기준원이 그래서 ⚠️ 로 나왔다.

고객사 5곳 실측 (사람이 다시 확인함):

| 사이트 | 결과 |
|---|---|
| 회계기준원 | ✅ 매일·과거 모두 (`?page={page}`) |
| 임팩트온 | ✅ 매일·과거 모두 — 브라우저 필요 |
| ESG Finance Hub | ⚠️ 매일만 — 브라우저 필요 · 쪽 번호가 주소에 없다 |
| 금융위원회 | ⚠️ 매일만 — 쪽 번호가 주소에 없다 |
| 잘못된 주소 | ❌ 못 연다고 이유까지 |

회계기준원의 쪽 번호는 내가 앞서 말한 `currentPageNo` 가 아니라 **`page`**
였다. 진단이 넷을 붙여 보고 실제로 넘어가는 것을 골라냈다.

### 54. 실제로 걸어 보고 나서야 드러난 셋

회계기준원에 감시를 걸고 기준선을 되돌려 돌렸다. 새 항목 9건 중 **셋이 왼쪽
메뉴**였다 — '한국 지속가능성 공시기준 적용지원' 같은 것. 낱말은 메뉴에도
걸린다. 적재 쪽에는 이미 규칙이 있었는데(날짜를 찍는 목록이면 날짜 없는 줄은
기사가 아니다) **감시 쪽에만 없었다.**

같이 드러난 둘: 그 항목들의 링크로 **감시 대상 주소가 그대로** 박혀
`{page}` 가 든 못 여는 주소가 볼트에 남았고, 한 기사가 **두 번** 올라왔다
(링크로 한 번, 줄로 한 번). 요약 LLM 이 "일부 중복 수집된 항목은 분석에서
제외"라고 적어 놓은 것이 힌트였다.

고친 뒤: 9건(메뉴 3·중복 1·깨진 링크 3) → **3건, 전부 실제 기사·진짜 주소.**

**그다음이 더 무거웠다.** 원문까지 읽기를 켜려다 켜기도 전에 드러났다.

    척도 2단계 = "제목만 확인됨 — 판단할 수 없다, **원문을 봐야 한다**"
    기본 문턱  = 4단계 이상

목록 감시의 1차 요약은 제목만 본다. 그래서 거의 다 2단계가 나온다. 문턱을
그대로 적용하면 **"원문을 봐야 한다"고 판정된 것이 문턱 미달로 안 열린다** —
기능이 통째로 헛돌았다. 켜 놓고도 아무 일이 없으니 고장인 줄도 몰랐을 것이다.
2단계는 낮은 점수가 아니라 **모른다는 표시**다. 문턱으로 거르지 않는다.
비용은 건수 상한과 본문 키워드가 잡는다 — 원래 그 둘의 일이다.

켜고 돌리니 같은 기사가 이렇게 바뀌었다.

    끄면: "제목만 확인됨 — 원문 확인 필요" (2/5)
    켜면: "자산 10조원 이상 99개사의 KSSB 부합도 분석 결과 Scope 1·2·3
          총량 공시 충족률 72.7%, 전환위험(8.1%)·물리적위험(10.1%) 노출
          자산의 재무적 영향까지 공개한 기업은 극히 저조" (3/5)

**ESG Finance Hub 는 켤 대상 자체가 없었다.** 날짜 붙은 항목 10건, 주소 있는
것 **0건**. DOM 을 뜯어 보니 제목은 `href="javascript:;"` 인 껍데기 링크이고
진짜 주소는 **`onclick="window.open('...')"` 안에** 있었다. 국내 포털에 흔한
방식인데 `<a href>` 만 훑던 우리는 통째로 놓쳤다.

세 겹으로 고쳤다 — onclick·data-url 에서 주소를 건지고, 제목은 그 태그의
글자(매체명 '라이센스뉴스')가 아니라 **카드의 첫 긴 줄**을 쓰고, 줄에서 나온
항목에 그 주소를 **이어 붙인다**. 결과 10건 중 0건 → **11건 전부**.

그러고 나서 돌린 ESG Finance Hub: 새 항목 5건, 문턱 위 3건의 원문을 열어
"국가 건물에너지 통합관리시스템 데이터와 금융 서비스를 연계한 공동 ESG
금융상품 검토" 같은 요약이 나왔다. 엔티티 5건 신규.

처음 이 사이트를 봤을 때 "403 으로 막혀 안 된다"고 했던 곳이다. 지금은 **가장
잘 도는 축**에 든다.

회귀 11종 · 451항목 통과.

### 55. 만들어 두고 한 번도 통하지 않았던 길

버전 0.1.0 → **0.2.0**, 첫 릴리스, 다운로드 페이지, `releases/latest.json`.
넷을 한 줄로 이어 붙이고 나서야 **자동 업데이트가 처음으로 완주했다** — 만든
날부터 그날까지 그 경로는 계속 404 였다. 고객이 겪기 전에 우리가 먼저 겪는
쪽을 골랐을 뿐인데, 겪어 보니 막힌 곳이 둘이었다.

`anfilt-releases` 가 **빈 저장소**라 릴리스 생성이 422 로 튕겼다(GitHub 는
커밋이 하나도 없는 저장소에 태그를 달지 못한다). README 하나로 씨를 뿌렸다.
그리고 **다운로드 주소에 버전을 박지 않았다** — `releases/latest/download/…`
는 다음 릴리스에도 그대로 유효하다. 페이지를 고쳐야 할 자리를 하나 없앴다.

버전·크기·해시는 페이지에 손으로 적지 않고 `latest.json` 에서 읽는다. 손으로
적으면 다음 릴리스 때 **페이지가 조용히 거짓말을 한다.**

### 56. 팩 회전 — 그리고 이름 바꾸기를 사람에게 시킨 값

프롬프트 팩 0.2.0 → **0.3.0**. 회전은 유출 대비책이다(→ [[26 팩을 저장소
밖으로]]). 32개 중 손댄 것은 `watch.digest` 둘뿐이다 — 54번에서 **실측으로
드러난 것만** 고쳤다. 근거 없이 문장을 바꾸면 회전이 아니라 그냥 흔드는 것이다.

    관점을 맨 위로            · 요약이 나열이 아니라 판단이 되게
    "제목만 확인됨" 강제 삭제 · 제목이 말하는 것까지 버리지 말 것
    메뉴·분류명은 importance 1 · 단계를 한 값으로 몰지 말 것

옛 팩과 새 팩으로 **같은 항목을 각각 요약해 비교**하고 넘겼다.

여기서 사고가 하나 났다. 나는 `pack-0.3.0.json` 으로 구워 놓고 "올릴 때 이름을
`pack.json` 으로 바꾸세요"라고 안내했다. 버킷에는 `pack-0.3.0.json` 만 남았고
서버는 팩을 찾지 못했다 — `config_error`, **새 활성화가 통째로 막혔다**(이미
깔린 설치본은 캐시로 계속 돌았다. 설계대로다). 사람에게 이름 바꾸기를 시키는
절차는 언젠가 반드시 어긋난다. `make_pack.py` 가 **언제나 `pack.json` 으로만
굽도록** 고쳤다. 바꿀 것이 없으면 어긋날 것도 없다.

### 57. `main` 병합 — R1 을 처음 건드린 순간

54개 커밋을 fast-forward 로 `main` 에 올렸다. 라이브 체험판은 그 가지에서
배포된다 — **실제로 R1 을 건드린 첫 순간**이었다.

병합 전에 기준선을 잡고(비밀번호 화면), 병합 후 같은 자리를 다시 보고, 새
코드가 정말 배포됐다는 증거(`/설정` 페이지)까지 확인한 뒤 로그인해 들어갔다.
📡 모니터링이 통째로 뜨고, 설치판 전용 기능은 **조용히 깨지지 않고 그렇다고
말했다.**

    과거 자료 적재  → "설치판 전용입니다"
    이 PC 자동 실행 → 섹션 자체가 없음 (리눅스에 작업 스케줄러가 없다)
    읽는 방식 3갈래 → 비활성 (Edge·Chrome 을 못 찾음 → 예전처럼 그냥 읽기)

병합 직전에 하나를 더 잡았다. `resolved_browser` 를 되적는 코드가 **체험판에서
매 점검마다 쓸모없는 쓰기**를 날리고 있었다 — 거기 `ra_watches` 에는 그 열이
없어 조용히 버려진다. 적어 둘 수 있는 저장소에서만 적도록 막고 시험을 붙였다.

### 58. 설치까지는 안내했지만, 그 다음은 안내한 적이 없다

홈페이지에 문서 두 장을 올렸다.

    /guide/install/   준비물 → 첫 조사까지 11단계 · 문제 해결표
                      · 무엇이 어디에 저장되나(전산팀 승인용 표)
    /guide/manual/    화면 넷의 칸마다 무슨 뜻인지 · 비용 줄이는 법
                      · 자주 묻는 것

내려받기 페이지의 네 칸 요약으로 설치를 끝낼 수 있는 사람은 **이미 아는
사람뿐**이었다. 파란 경고창에서 무엇을 눌러야 하는지, 앱 비밀번호가 메일로
오지 않는다는 것, 페이지 감시의 첫 회가 왜 조용한지 — 물어볼 곳이 문의
게시판밖에 없었다. 상단 메뉴에는 넣지 않았다(메뉴가 일곱이면 모바일에서
접히고, 공용 chrome 을 일곱 파일에서 맞춰야 한다). 찾는 사람은 내려받기
페이지에 오므로 **내려받기 단추 바로 아래**에 뒀다.

**하다가 이미 라이브인 버그를 하나 밟았다.** `download.html` 에만
`prefers-color-scheme:dark` 분기가 있었는데, 공용 `site.css` 에는 그 분기가
**하나도 없다** — 종이·잉크 한 벌로 고정된 브랜드다. 그래서 OS 를 다크로 둔
방문자에게는 배경만 `#2a2114` 로 어두워지고 글자는 잉크색 `#1b1813` 그대로였다.
대비 1.2:1, 사실상 안 보인다.

하필 그 상자가 **SmartScreen 안내**다. 경고를 보고 겁먹은 사람이 읽어야 할
글이 그 사람에게만 안 보였다. 분기를 지우고 왜 두면 안 되는지 주석으로 남겼다.
새 문서 두 장에도 같은 것을 넣을 뻔했다가 **실측(대비 13:1 확인)으로** 잡았다.

### 59. 유출된 키를 갈다가 — 한 번에 하나씩 아니면 못 찾는다

2026-08-15 스크린샷으로 샌 `SUPABASE_SERVICE_ROLE_KEY` 를 갈았다. 반나절이
걸렸는데, 열쇠를 바꾸는 일 자체는 5분이고 나머지는 **틀린 전제 넷을 하나씩
깨는 데** 썼다. 넷 다 눌러 보기 전에 잡혔지만, 셋은 내가 먼저 틀리게 말했다.

**① 프로젝트가 둘인데 하나로 알았다.** 나는 `docs/27` 의 라이선스 프로젝트
주소를 그대로 드리면서 `.env` 의 변수를 갈자고 했다 — 그 변수는 **다른
프로젝트** 것이다. 사장님이 만든 첫 키는 엉뚱한 곳의 키였다.

**② "접근 불가"는 접근 불가가 아니었다.** `koorjatscpkvomjosenc` 에 들어가려니
`You do not have access to this project`. `docs/12`·`docs/24` 에 그렇게 적혀
있으니 나는 "영영 관리 못 한다, 데이터를 통째로 옮기자"까지 갔다. **계정이
둘**이었다. gmail 과 hanmail(GitHub 연동), 프로젝트가 하나씩. 로그인만 바꾸면
됐다. 설계서를 고쳤다 — 프로젝트를 적을 때 **어느 계정 것인지 함께** 적는다.

**③ 라이브 체험판이 실제로 깨졌다.** Streamlit 시크릿에 키가 **바뀌어**
들어갔다(라이선스 키를 체험판에). 화면은 멀쩡히 떴다 — 비밀번호 화면도,
조사 화면도. 로그인해서 📡 모니터링에 들어가서야 나왔다.

    감시 목록 조회 실패: Supabase 401: {"message":"Invalid API key"}

**첫 화면이 뜨는 것은 아무 증명도 아니다.** 저장소를 실제로 건드리는 화면까지
들어가 봐야 한다. 3분 만에 고쳤는데, 그건 그 직전에 바꾼 것이 하나뿐이라
어디를 볼지 알았기 때문이다.

**④ `needEnv` 순서에 함정이 있었다.** Edge Function 은 이렇게 찾았다.

    needEnv("SUPABASE_SERVICE_ROLE_KEY", "SB_SECRET_KEY", ...)

legacy 를 끄면 이 변수는 **값이 남은 채 죽는다** — Supabase 가 자동 주입하므로
사라진다는 보장이 없다. `needEnv` 는 값이 있는지만 보고 통하는지는 안 본다.
그러면 새 키를 제대로 심어 두고도 함수가 죽은 키를 집어 든다. 순서를 뒤집고
(`SB_SECRET_KEY` 우선) 다시 배포한 **뒤에** legacy 를 껐다. 껐는데 그대로
도는 것을 보고서야 새 키로 넘어갔다고 말할 수 있었다.

그리고 검증하다 **좌석 하나를 내가 먹었다.** 진짜 키로 활성화를 시험해
가짜 기기가 좌석 2번을 차지했다. 없는 키로도 충분한 시험이었다. 지웠다.

    라이선스 프로젝트   sb_secret_ 로 교체 · legacy 꺼짐        ✅
    체험판 프로젝트     sb_secret_ 로 교체 · legacy 살아 있음   ⚠️
    액세스 토큰         양쪽 계정 모두 없음 (이미 사라짐)        ✅

**체험판 쪽 legacy 를 못 끈 이유**는 비활성 버튼이 `service_role` 과 `anon` 을
함께 끄기 때문이다. 홈페이지 `site.js`·`editor.js`·`admin.html` 셋이 그
프로젝트의 anon 키를 박아 쓴다 — 지금 끄면 **상담 폼과 게시판이 죽는다.**
anon → publishable 교체가 선행 조건이다 (→ [[12 홈페이지 제품 페이지와 상담 관리]]).

곁가지로 하나 더 드러났다. **체험판의 자동 감시는 한 번도 돈 적이 없다.**

    2026-08-09 12:54  자동 모니터링  failure
    ❌ Supabase 미설정 — SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY 필요

GitHub Actions 에 시크릿이 하나도 없다. 계속 실패해서 8월 9일 이후로는 스케줄
자체가 꺼졌다. 미검증 표의 "Actions Secrets" 가 이것이었고, 이제 원인까지
