# 15 자동 모니터링과 알림

특정 사이트·키워드를 **정해진 시각에 자동 점검**해 새로운 내용만 잡아내고,
요약을 지식볼트에 축적한 뒤 이메일·카카오톡으로 알린다.
사용자 요청(2026-08-05): *"매일 정해진 시간에 검색해서 새로운 내용이면 요약
보고하고 옵시디언 볼트에 축적, 나에게는 카톡이나 메일로 알림"*.

관련: [[13 지식 볼트와 온톨로지]] · [[16 지식 비서]] · [[14 라이트 모드]]

## 전체 그림

```
GitHub Actions (매시 정각 cron)
        └─▶ watch_run.py ─▶ core.watch_runner.run_due_watches()
                                    │
             ┌──────────────────────┼───────────────────────┐
             ▼                      ▼                       ▼
        1. 점검(코드)          2. 요약(경량 LLM)      3. 축적·알림
        page: 링크·본문 diff    새 항목만 브리핑       볼트 watch/ 노트
        keyword: 웹검색         중요도 1~10           엔티티 업서트
        → 지문으로 새것 판별                          → 이메일·카톡

Streamlit 앱 (pages/1_📡_모니터링.py)
        └─▶ 등록·설정·수동 점검·수집 이력 열람 (같은 run_watch 호출)
```

## 설계 원칙

### 1. '새로움'은 코드가 판정한다 — LLM에게 묻지 않는다
LLM에게 "이거 새로운 소식이야?"를 물으면 판정이 매 실행마다 흔들리고 비용도
든다. 판정은 **지문(fingerprint)** 으로 한다.

| 감시 종류 | 지문 | 새 항목의 정의 |
|---|---|---|
| page | 정규화 URL 해시 (`u:…`) | 페이지의 링크 중 `ra_watch_seen`에 없는 것 |
| page | 본문 증가분 해시 (`t:…`) | 직전 스냅샷에 없던 줄이 200자 이상 |
| keyword | 정규화 URL 해시 | 검색 결과 중 아직 못 본 URL |

URL 정규화는 `utm_*`·`fbclid`·프래그먼트·꼬리 슬래시를 제거한다 — 같은 글이
추적 파라미터만 달라 매일 '새 소식'으로 잡히는 것을 막는다.

LLM은 **이미 새롭다고 확정된 것의 요약만** 맡는다. 이 분업이 비용과 신뢰성을
동시에 잡는다.

### 2. 첫 실행은 기준선(baseline)이다 — page 감시만
목록 페이지를 처음 감시하면 기존 링크 수십~수백 개가 전부 '새 항목'이다
(실측: 환경부 보도자료 목록 = 153개). 이걸 알리면 알림이 무의미해지므로
**첫 회는 지문만 적재하고 조용히 끝낸다.**

키워드 감시는 반대로 첫 회부터 보고한다 — 검색 결과는 애초에 최근 10건
이내로 큐레이션돼 있어 첫 알림 자체가 유용하기 때문이다
(`watch_runner.BASELINE_KINDS`).

### 3. 알림보다 축적이 먼저
실행 순서는 **볼트 축적 → 지문 기록 → 알림**이다. SMTP·카카오 토큰이 만료돼도
지식은 이미 볼트에 남아 있고, 다음 점검에서 같은 항목을 중복 보고하지 않는다.
알림 실패는 `last_status`에 남겨 앱에서 볼 수 있게 한다.

### 4. 스케줄은 앱 바깥에 있어야 한다
Streamlit Cloud 앱은 **접속 중일 때만 살아 있다** — 브라우저를 닫으면 세션이
없어지므로 앱 안의 타이머로는 "매일 08시"를 지킬 수 없다. 그래서:

- 스케줄 실행 → **GitHub Actions** (`.github/workflows/watch.yml`, 매시 정각 cron)
- 등록·설정·수동 실행·열람 → Streamlit 페이지

둘은 **같은 함수(`run_watch`)** 를 부른다. 수동 실행과 자동 실행의 동작이
갈라지면 "앱에선 되는데 자동은 안 된다"는 진단 불가능한 상황이 생긴다.

cron이 매시 정각인 이유: GitHub cron은 UTC이고 감시별 실행 시각은 KST라,
"매시 깨워서 지금이 그 시각인 감시만 고른다"가 가장 단순하다(`watch.is_due`).
같은 시각대 중복 실행은 `last_checked_at`의 (날짜, 시)로 막는다.

## 데이터 모델 (`supabase-ra-watch-setup.sql`)

- `ra_watches` — 감시 1건 = 1행. `hours`는 KST 시각 CSV(`"08,18"`),
  `notify`는 채널 CSV(`"email,kakao"`), `last_snapshot`은 page 감시의 직전 본문.
- `ra_watch_seen` — `(watch_id, fingerprint)` 기본키. 이 테이블에 **없다는 것**이
  새로움의 정의다.

접근 모델은 `ra_runs`·`ra_vault`와 동일 — service_role만, anon/authenticated
전면 차단(감시 키워드에 고객사 정보가 섞일 수 있다).

## 모듈 구성

| 파일 | 역할 | Streamlit 의존 |
|---|---|---|
| `core/watch.py` | 순수 로직 — 지문·수집·diff·요약 프롬프트·노트/알림 렌더 | ✗ |
| `core/watch_runner.py` | 배선 — 점검→요약→볼트→지문→알림 | ✗ |
| `core/notify.py` | 이메일(SMTP)·카카오톡(memo API) 발송 | ✗ |
| `core/vault_sync.py` | 시드 초기화 (app.py에서 분리 — CLI도 써야 하므로) | ✗ |
| `watch_run.py` | 스케줄러 진입점 CLI | ✗ |
| `pages/1_📡_모니터링.py` | 등록·설정·수동 점검·이력 | ✓ |

## 호출 비용 (경량 모델 기준)

| 상황 | 호출 수 |
|---|---|
| page 감시, 새 항목 없음 | **0회** (HTTP 1회뿐) |
| page 감시, 새 항목 있음 | 2회 (요약 1 + 엔티티 추출 1) |
| keyword 감시, 새 항목 없음 | 2회 (웹검색 1 + 구조화 1) |
| keyword 감시, 새 항목 있음 | 4회 |

`generate_json`에는 검색 도구가 붙지 않으므로 키워드 감시는 라이트 모드와 같은
2단계(웹 검색 → 구조화)로 나눈다(→ [[14 라이트 모드]]).

## 볼트 축적

새 항목이 있으면 `watch/<날짜> <감시명>.md` 노트를 만들고, 조사 결과와 **같은
경로로** 엔티티에도 반영한다(`ontology.extract_entities` → `apply_extraction`).
그래야 모니터링으로 들어온 사실을 [[16 지식 비서]]가 답변 근거로 쓸 수 있다.

노트에는 조사 노트와 같은 미검증 라벨(`tags: [watch, 자동수집, 미검증]` +
콜아웃)을 붙인다 — 자동 수집물이 검증된 사실로 세탁되지 않게 하는
[[13 지식 볼트와 온톨로지]]의 원칙 그대로다.

## 알림 채널

**이메일(SMTP)** — 전문(제목·요약·항목별 무엇이/왜·원문 링크)을 보낸다.
Gmail은 2단계 인증 + 앱 비밀번호.

**카카오톡** — `/v2/api/talk/memo/default/send` (나에게 보내기)만 쓴다.
친구에게 보내기는 카카오 검수가 필요하지만 나에게 보내기는 토큰만 있으면 된다.
액세스 토큰은 6시간이면 만료되므로 **매 실행마다 리프레시 토큰으로 갱신**한다.
텍스트 템플릿 상한이 200자라 190자에서 자른다(초과하면 400 실패).

## 알려진 한계

- **SPA(자바스크립트로 그리는 페이지)** 는 `requests`로 빈 HTML만 온다.
  실측: `unfccc.int/news` → 링크 0·본문 0. 조용히 '변경 없음'이 되지 않도록
  명시적 오류를 던져 RSS·목록 페이지·키워드 감시로 바꾸도록 안내한다.
  (Playwright 도입은 [[09 향후 고도화 백로그]])
- 봇 차단(403) 사이트가 있다 — 실측: `iso.org`. 키워드 감시로 우회.
- 목록 페이지의 새 링크에는 메뉴·배너가 섞일 수 있다. 기준선이 대부분 흡수하고,
  요약 단계에서 중요도(1~10)로 걸러진다.
- 한 번에 요약·알림하는 새 항목은 8건까지(`MAX_HITS`). 초과분도 지문은 기록되고
  노트의 '원본 링크' 절에는 전부 남는다.
- **GitHub cron은 정시를 보장하지 않는다** — 러너 혼잡 시 수십 분 밀릴 수 있다.
  "08시대에 한 번"이 실제 의미다(`is_due`가 시각대 단위로 판정하는 이유).
- **저장소가 60일간 조용하면 GitHub이 스케줄 워크플로를 자동 중지**한다. 앱을
  안 건드리는 기간이 길어지면 Actions 탭에서 재활성화하거나 수동 실행이 필요하다.
- 검색 LLM이 기사 대신 언론사 홈 주소만 주는 경우가 있다(실측). 그 URL로 지문을
  만들면 같은 매체의 다음 기사가 전부 '이미 본 것'이 되므로, 경로 없는 URL은
  제목 기반 지문으로 전환한다(`has_deep_path`).
