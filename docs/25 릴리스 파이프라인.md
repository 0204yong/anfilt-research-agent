# 25 릴리스 파이프라인

> 설계는 [[19 두 제품 구성과 자동 업데이트]] 4~5절, 라이선스 쪽은 [[24 라이선스 서버 배포]].
> **이 문서는 "새 버전을 내보내는 순서"** 다.

## 저장소가 셋인 이유

| 저장소 | 공개 | 담는 것 |
|---|---|---|
| `0204yong/anfilt-research-agent` | **공개** ⚠️ | 소스·프롬프트·시드 |
| `0204yong/anfilt-releases` | **공개** | 설치 파일·델타 zip **만** |
| `0204yong/anfilt-homepage` | 비공개 | 홈페이지 + `releases/latest.json` |

설치 파일을 소스와 **다른 저장소**에 두는 이유: 비공개 저장소의 Releases 자산은
인증을 요구하고, 고객 PC 의 자동 업데이트에는 토큰이 없다. 소스 저장소를 언젠가
비공개로 돌리더라도 배포가 멈추지 않도록 처음부터 갈라 둔다. 릴리스 저장소에는
소스가 없으므로 공개돼도 잃을 것이 없다.

### ⚠️ 아직 열려 있는 구멍

소스 저장소가 공개라 **`vault_seed/` 35노트와 프롬프트를 누구나 받을 수 있다.**
[[20 라이선스와 복제 방지]]는 그것이 이 제품의 값어치라고 못 박고 있으므로,
지금 상태에서는 라이선스 서버가 지킬 것이 사실상 없다.

**비공개 전환은 실패했다** (2026-08-14). 체험판이 Streamlit Community Cloud 에서
이 저장소를 읽는데, 비공개로 바꾸는 순간 "Error running app" 으로 죽었다.
Streamlit 워크스페이스 설정에는 비공개 저장소 접근 권한을 주는 항목이 없고
`Disconnect` 뿐이라, 연결을 끊었다 다시 잇는 길밖에 없다 — 라이브 체험판을
걸고 할 일이 아니다.

**가야 할 방향**: 저장소는 공개로 두고 **값어치 있는 것만 서버 뒤로** 옮긴다.
`vault_seed/` 와 프롬프트를 저장소에서 빼고, 체험판도 설치판과 같은 팩 인출
경로를 쓰게 한다. 그러면 공개 저장소에는 코드만 남고, 프롬프트를 고칠 곳도
한 군데가 된다.

매니페스트를 홈페이지에 두는 이유: 파일 하나만 갈아 끼우면 되고, GitHub 이
막힌 망에서도 홈페이지는 대개 열린다.

## 버전 정하기

`packaging/VERSION` 한 곳이 진실이다. 설치판·델타·매니페스트가 모두 이걸 읽는다.

- **델타로 충분한가** — 파이썬 런타임과 의존성이 그대로면 델타(수 MB)로 간다.
  `requirements` 를 건드렸으면 `-PyVersion` 이 같아도 **전체 설치 파일**을 내야 한다.
- `min_supported` 를 올리는 것은 **옛 버전을 끊는 것**이다. 프롬프트 스키마나
  모델 ID 가 바뀌어 옛 버전이 조용히 고장 날 때만 올린다 (→ [[19 두 제품 구성과 자동 업데이트]] 4.5).

## 1. 굽기

```powershell
.\packaging\build.ps1
```

`%LOCALAPPDATA%\Temp\ra-build\dist\releases\` 에 셋이 나온다.

- `app-<버전>.zip` — 델타
- `*Setup*.exe` — 설치 파일 (Inno Setup 이 깔려 있을 때)
- `latest.json` — 매니페스트 (sha256·크기가 이미 박혀 있다)

> 팩·시드는 **빠진 채로** 구워진다. 공개키는 `core/licensing.py` 에 박혀 있으므로
> 플래그가 필요 없다. 시연용으로 팩을 넣으려면 `-IncludePack` (→ [[24 라이선스 서버 배포]]).

## 2. 자산 먼저, 매니페스트 나중 ⚠️

**이 순서를 뒤집지 말 것.** 매니페스트가 먼저 올라가면 고객의 앱은 아직 없는
파일을 받으러 가서 실패한다 — 그것도 "업데이트가 있다"고 알린 직후에.

```powershell
gh release create v<버전> -R 0204yong/anfilt-releases `
  "<릴리스폴더>\app-<버전>.zip" "<릴리스폴더>\*Setup*.exe" --title "v<버전>"
```

올라간 자산 주소가 매니페스트의 `url` 과 **글자 그대로** 같아야 한다.
`build.ps1 -ReleaseBase` 가 그 주소를 만든다.

## 3. 매니페스트 올리기

`latest.json` 을 홈페이지 저장소 `releases/` 에 복사하고 푸시하면 Netlify 가
`https://anfilt-homepage.netlify.app/releases/latest.json` 로 배포한다.

```powershell
Copy-Item "<릴리스폴더>\latest.json" "C:\ANFILT_AI\Company_Homepage\releases\latest.json"
```

> `netlify.toml` 은 이 파일이 **없어도 빌드를 실패시키지 않는다**. 다른 페이지와
> 다르게 다루는 이유는, 매니페스트 하나 때문에 홈페이지 전체가 내려가는 편이
> 더 나쁘기 때문이다. 대신 빌드 로그에 `no releases/latest.json` 이 남는다.

## 4. 확인

```powershell
curl.exe -s https://anfilt-homepage.netlify.app/releases/latest.json
```

그다음 **실제 설치판에서** ⚙️ 설정 → 업데이트 → 지금 확인. 받고, 재시작되고,
버전이 올라가는 것까지 본다. 매니페스트만 보고 끝내지 않는다 —
[[23 설치판 구현 계획]] 6단계에서 잡힌 결함들은 전부 실제로 눌러 봐야 나왔다.

## 되돌리기

**매니페스트를 옛 버전으로 되돌리는 것**이 가장 빠르다 (자산은 지우지 않는다).
이미 올라간 고객은 그대로 두고, 아직 안 받은 고객만 멈춘다.

급하면 홈페이지 저장소에서 `releases/latest.json` 을 지우고 푸시한다 —
404 는 클라이언트가 "연결하지 못했습니다"로 조용히 넘긴다(→ `core/updates.py`).

## 실패했을 때 어디를 보나

| 증상 | 먼저 볼 곳 |
|---|---|
| "업데이트 서버에 연결하지 못했습니다" | 매니페스트 404 · Netlify 빌드 로그 |
| 받다가 "파일이 손상되었습니다" | sha256 불일치 — **자산을 다시 올렸는데 매니페스트가 옛것** |
| "새 버전이 있지만 받을 파일 정보가 없습니다" | `url`/`sha256` 중 하나가 비었다 |
| 델타를 받았는데 버전이 그대로 | `app/version.json` 확인 (→ [[23 설치판 구현 계획]] 6단계) |
| 자산 주소가 401/404 | 비공개 저장소에 올렸다 — `anfilt-releases` 로 |
