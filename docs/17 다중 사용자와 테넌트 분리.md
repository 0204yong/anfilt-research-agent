# 17 다중 사용자와 테넌트 분리

> 상태: **설계 완료 · ⏸ 보류 (2026-08-07)**.
> 같은 날 나온 [[18 설치형 패키지]](사용자 PC 설치 + 본인 API 키 + 본인 옵시디언
> 폴더)가 **권장안으로 채택**되면서, 이 문서가 푸는 문제 12건 중 10건이 착수 없이
> 사라진다. 폐기하지 않고 남겨 둔다 — "여러 명이 **하나의 볼트를 함께** 키우고
> 싶다"는 요구가 실제로 나오면 그때 여기서 재개한다.
> 아래 1절의 결함 진단은 **호스팅 상태를 유지하는 한 그대로 유효**하다.
>
> [[13 지식 볼트와 온톨로지]] 로드맵 5단계("GitHub 동기화 + 다중 사용자")를
> 실제 요구에 맞춰 확장·대체한 문서이기도 하다.

## 요구 (사용자, 2026-08-07)

1. 리서치 에이전트를 **다른 사람도 쓰게** 한다 — 대상은 **고객사 대상 유료 서비스**
2. 지식볼트(온톨로지)는 **사용자별 완전 분리** — 남의 볼트가 섞이지 않는다
3. 시작점은 **옵시디언(지식볼트) 연결** — 볼트가 1인용으로 묶여 있는 구조부터 푼다

## 결론 요약

- 격리 단위는 **테넌트(고객사) 1개 = 볼트 1개**. 1인 고객사면 곧 "사용자별 완전
  분리"와 같고, 담당자가 2명이 되어도 스키마를 안 고친다 (인수인계·퇴사 대응).
- 격리는 **DB(RLS)가 강제**한다. 앱 코드의 `where tenant_id=` 는 잊으면 유출이지만,
  RLS는 잊을 수 없다. 지금 구조(service_role 단일 키 + RLS 전면 차단)는 1인용으로는
  최선이었으나 다중 테넌트에서는 **가장 위험한 부분**이다.
- 옵시디언 연결은 3단계로 승격한다: **① 테넌트별 zip 왕복 + 병합·되돌리기 →
  ② Dropbox/OneDrive 앱 폴더 자동 동기화 → ③ GitHub 비공개 repo**.
  구글 드라이브 양방향은 함정이 있다(아래 3.1).
- 유료화의 진짜 게이트는 인증이 아니라 **비용 방어**다. 실행 1건이 멀티 LLM
  수십 회 호출이므로, 한도 없이 계정을 열면 대표 카드가 먼저 터진다.

## 1. 현재 상태 진단 — 2인째부터 어디가 깨지는가

코드 기준 실사(2026-08-07). "언젠가 문제"가 아니라 **두 번째 사용자가 들어온
당일 사고가 나는 것**부터 적는다.

| # | 지점 | 지금 동작 | 2인째에 벌어지는 일 |
|---|---|---|---|
| 1 | `ra_vault` PK = `path` | 서버 볼트가 **전역 1개** | B의 조사가 A의 노트에 축적된다. 고객사 자료 혼입 |
| 2 | `store.vault_replace_all` | `DELETE ra_vault?path=like.*` **전체 삭제** 후 적재 | B가 zip을 올리면 **A의 볼트가 통째로 사라진다** |
| 3 | `vault_sync.ensure_vault_seeded` | "볼트가 비었으면" 판정이 전역 | 새 고객사에게 시드가 안 깔림(이미 남의 볼트가 차 있으므로) |
| 4 | `ra_runs` / `ra_watches` / `ra_watch_seen` | 전부 전역 | 사이드바 "이전 조사"에 **남의 고객사 주제가 보인다** |
| 5 | `ui_common.require_password` | `APP_PASSWORD` **공유 1개** | 사용자 구분 자체가 없음. 해지·개별 차단 불가 |
| 6 | `st.cache_data` 3곳 (`_list_runs_cached`, 감시 목록, 볼트) | 캐시 키에 사용자가 없음 | **캐시 히트로 남의 데이터가 그대로 렌더된다** (테넌트 컬럼만 추가하고 이걸 놓치면 유출) |
| 7 | `bridge_secrets_to_env` → `os.environ` | 프로세스 전역 | Streamlit 1프로세스 = 다중 세션. **사용자별 값을 env에 넣는 순간 옆 사용자에게 샌다** |
| 8 | 프로바이더 생성자 | `anthropic.Anthropic()` / `OpenAI()` — 키를 **env에서 암묵적으로** 읽음 | 고객사 자체 키(BYO) 주입 경로가 없음. 7번과 합쳐 BYO의 선결 조건 |
| 9 | `notify.email_recipient()` | `NOTIFY_EMAIL_TO` 전역 1개 | 모든 고객사의 모니터링 알림이 **대표 메일 한 곳으로** 간다 |
| 10 | `watch_run.py` / `watch_runner.run_due_watches` | 활성 감시 전부 순회 | 실행 비용의 귀속처가 없고, 실패 1건이 전 고객사 배치에 섞인다 |
| 11 | API 키·과금 | 대표 키 1벌, 사용량 계측 없음 | 유료로 팔면서 **원가를 모른다**. 한도 없음 = 무제한 청구 |
| 12 | 접근 모델 | service_role 키 하나로 전체 접근 | 코드가 필터를 한 번만 빠뜨려도 **교차 테넌트 유출** |

3.의 보조 관찰: `librarian.py`·`ontology.py`·`vault_render.py` 는 `{path: content}`
dict만 받으므로 **테넌트화의 영향이 없다**. 바꿔야 하는 건 "볼트를 어디서
불러오는가" 한 겹뿐이다 — 이 설계가 값싸게 끝나는 이유.

## 2. 격리 단위 — 왜 user_id 가 아니라 tenant_id 인가

요구는 "사용자별 완전 분리"지만, 키를 `user_id` 로 박으면 다음이 전부 스키마
변경을 부른다: 고객사 담당자가 2명이 되는 순간 / 담당자가 퇴사해 인수인계하는
순간 / 대표가 고객사 볼트를 대신 봐줘야 하는 순간(유료 서비스에서는 지원 업무로
반드시 생긴다).

그래서 **`tenant_id` 를 격리 키로 두고, 기본 상태는 "테넌트 1개에 사용자 1명"**
으로 시작한다. 이 상태에서의 동작은 요구한 "사용자별 완전 분리"와 정확히 같고,
나중에 사람을 붙이는 것은 `ra_members` 에 한 행 추가로 끝난다.

```
ra_tenants (고객사)  1 ──< ra_members (auth.users) N
     │
     └──< ra_vault · ra_runs · ra_watches · ra_watch_seen · ra_usage   (전부 tenant_id 보유)
```

## 3. 확정 설계

### 3.1 옵시디언 볼트 연결 (요구의 출발점)

원칙은 [[13 지식 볼트와 온톨로지]] 그대로 유지한다 — **마크다운이 원본이고,
서버 테이블은 작업 사본**. 다만 유료 고객사에서는 사본이 사실상 상시 정본처럼
쓰이므로 **되돌릴 수 있어야** 한다.

#### 1단계 (필수) — 테넌트별 zip 왕복 + 병합·스냅샷

지금의 zip 왕복은 **"교체"** 다. 1인용일 땐 "사용자 우선"이라는 좋은 규칙이지만,
유료 다중 사용자에서는 두 가지 사고를 만든다.

- **스테일 zip**: 월요일에 받은 zip을 금요일에 올리면, 그 사이 조사·모니터링이
  자동 축적한 노트가 **경고 없이 전부 소멸**한다.
- **남의 zip**: 고객사 A의 볼트를 B 계정에서 실수로 올려도 지금은 그냥 들어간다.

바꾸는 것:

1. **내보내기 zip에 `_meta/export.json` 을 심는다** — `{tenant_id, exported_at,
   file_count, hashes:{path: sha1}}`. (Obsidian에서는 그냥 조용한 파일 하나다.)
2. **업로드 시 tenant_id 대조** — 다르면 **거부**. 다른 고객사 볼트 혼입은
   기능 문제가 아니라 계약 문제다 ([[13 지식 볼트와 온톨로지]] 안전장치 3의 승격).
3. **교체 대신 3-way 병합** (`store.vault_merge` 신설). 기준선은 `exported_at`:

   | zip | 서버 | 판정 |
   |---|---|---|
   | 있음 | 없음 | 추가 (사용자가 Obsidian에서 만든 새 노트) |
   | 있음 = 서버 | — | 무시 |
   | 있음 ≠ 서버, 서버가 `exported_at` 이후 **안 바뀜** | | **zip 우선** (사용자 편집 반영 — 기존 원칙) |
   | 있음 ≠ 서버, 서버도 그 사이 **바뀜** | | **충돌**: zip을 정본으로 쓰되 서버본을 `_conflict/<경로> (YYYY-MM-DD).md` 로 보존하고 화면에 목록 표시 |
   | 없음 | 있고 `exported_at` **이후** 생성 | **지우지 않는다** (내보낸 뒤 쌓인 자동 축적분 — zip에 없는 게 당연) |
   | 없음 | 있고 `exported_at` **이전**부터 존재 | **삭제 후보**로 제시, 사용자가 체크한 것만 삭제 |

4. **병합 직전 스냅샷** (`ra_vault_snapshots`, 테넌트당 최근 3개) + "되돌리기" 버튼.
   20분짜리 조사가 침묵 속에 증발하는 경로를 막는다는 문서 13 안전장치 4와 같은 계열.
5. `vault_replace_all` 은 남기되 **"고급 · 위험" 옵션으로 강등**하고 확인 문구를 건다.
6. `_meta/export.json` 이 없는 zip(옛 내보내기·수동 압축)은 `exported_at` 을 모르므로
   **보수적으로 병합**한다: 추가·변경만 반영하고 **삭제는 일절 하지 않는다**.

`parse_vault_zip` 의 최상위 폴더 방어와 볼트 아님 거부(2026-08-04)는 그대로 유효하며,
여기서 tenant 대조가 한 겹 더 얹히는 구조다.

#### 2단계 (권장) — 앱 폴더 자동 동기화 (Dropbox / OneDrive)

zip 왕복은 유료 고객에게 곧 "왜 매번 압축을 풀어야 하죠?"가 된다. 그런데
**구글 드라이브는 함정이 있다**:

- `drive.file` 스코프는 **앱이 만든 파일만** 보인다 → 사용자가 Obsidian에서 새로
  만든 노트를 앱이 **읽지 못해** 사실상 단방향이 된다(볼트 원본 원칙 위반).
- 폴더 전체 양방향에 필요한 `drive` 스코프는 **restricted scope** — 구글의 앱 검수와
  연 1회 CASA 보안 평가가 필요하다. 유료 서비스를 키운다면 언젠가 할 일이지만
  **초기 고객 5명을 위해 치를 비용은 아니다**.
- **Dropbox의 App folder 권한**(`/앱/리서치에이전트/` 아래 전체 읽기·쓰기)과
  **OneDrive의 `Files.ReadWrite.AppFolder`** 는 검수 없이 폴더 양방향이 된다.
  사용자는 그 폴더를 Obsidian에서 볼트로 열기만 하면 된다 — **git 지식 불필요**,
  ESG 실무자에게 현실적인 유일한 자동 경로.

동기화 규칙: 조사/감시 종료 시 **변경 파일만 push**, 조사 시작 시 **pull**.
충돌 판정은 1단계의 3-way 표를 그대로 재사용한다(구현이 두 벌이 되지 않게).

#### 3단계 (선택) — GitHub 비공개 repo + Obsidian Git

문서 13이 원래 예고한 경로. 사내 IT가 있는 고객사·파워유저에게만 노출한다.
PAT 발급·만료 관리 부담이 있어 기본값으로는 부적합.

연결 방식은 테넌트 속성(`ra_tenants.vault_link = zip | dropbox | onedrive | github`)
으로 고르게 하고, **어느 방식이든 서버 사본(`ra_vault`)이 중심 허브**다.
동기화 어댑터만 갈아 끼우는 구조여야 3단계가 1·2단계를 무효화하지 않는다.

#### 시드 온톨로지

테넌트 **생성 시 1회 복사**(35노트). 이후 repo 시드가 갱신돼도 자동 반영하지
않는다 — 사용자 큐레이션을 덮어쓰지 않는다는 `merge_entity` 원칙과 같다.
대신 "새 시드 노트만 가져오기" 버튼을 둔다(기존 노트 무수정).

### 3.2 저장 계층 — 스키마 변경

```sql
-- 신규
create table public.ra_tenants (
  tenant_id  uuid primary key default gen_random_uuid(),
  name       text not null,
  plan       text not null default 'trial',      -- trial|basic|pro
  vault_link text not null default 'zip',
  created_at timestamptz not null default now()
);

create table public.ra_members (
  user_id    uuid primary key references auth.users(id) on delete cascade,
  tenant_id  uuid not null references public.ra_tenants(tenant_id) on delete cascade,
  role       text not null default 'member',     -- owner|member
  created_at timestamptz not null default now()
);
create index ra_members_tenant_idx on public.ra_members(tenant_id);

-- 기존 4테이블: tenant_id 추가 + 키 재구성
alter table public.ra_vault add column tenant_id uuid not null
  references public.ra_tenants(tenant_id) on delete cascade;
alter table public.ra_vault drop constraint ra_vault_pkey;
alter table public.ra_vault add primary key (tenant_id, path);   -- ★ 1번 결함의 근원
alter table public.ra_runs       add column tenant_id uuid not null references public.ra_tenants(tenant_id) on delete cascade;
alter table public.ra_watches    add column tenant_id uuid not null references public.ra_tenants(tenant_id) on delete cascade;
alter table public.ra_watch_seen add column tenant_id uuid not null references public.ra_tenants(tenant_id) on delete cascade;
create index ra_runs_tenant_idx    on public.ra_runs (tenant_id, executed_at desc);
create index ra_watches_tenant_idx on public.ra_watches (tenant_id, enabled);
```

기존 1인용 데이터는 마이그레이션에서 테넌트 `기본(대표)` 한 건을 만들어
전부 backfill한다 (`not null` 은 backfill 후 부여).

### 3.3 격리를 **DB가 강제**하게 — 접근 모델 전환

지금은 앱이 service_role 키 하나로 모든 행에 닿는다. 테넌트 컬럼만 추가하고
필터를 앱 코드에 맡기면, **`where` 하나를 빠뜨린 날이 유출 사고 날**이다.
그래서 경로를 둘로 나눈다.

| 경로 | 키 | 격리 강제 주체 |
|---|---|---|
| **대화형(앱 화면)** | 로그인한 사용자의 **JWT** + anon 키 | **RLS** — 코드가 틀려도 DB가 막는다 |
| **배치(`watch_run.py`)** | service_role | 코드. 대신 **tenant_id 를 필수 인자**로 만들어 누락 시 `TypeError` |

```sql
-- 정책이 ra_members를 다시 읽으며 재귀하지 않도록 security definer 헬퍼
create or replace function public.current_tenant() returns uuid
language sql stable security definer set search_path = public as $$
  select tenant_id from public.ra_members where user_id = auth.uid()
$$;

create policy ra_vault_own on public.ra_vault for all to authenticated
  using (tenant_id = public.current_tenant())
  with check (tenant_id = public.current_tenant());
grant select, insert, update, delete on public.ra_vault to authenticated;
-- ra_runs · ra_watches · ra_watch_seen · ra_usage 도 동일 패턴
```

`core/store.py` 는 **모듈 전역 함수를 폐기하고 `Store` 객체**로 바꾼다.
"테넌트 없이 볼트를 부를 수 있는 함수가 존재하지 않는" 상태를 만드는 것이 핵심 —
문서 13의 zip 방어와 같은 사상("사람이 규칙을 지키게 하는 설계 → 코드가 보장하는 설계").

```python
class Store:
    def __init__(self, tenant_id: str, access_token: str = None):
        """access_token 있으면 사용자 JWT+anon(RLS 적용), 없으면 service_role(배치용)."""
    def vault_list(self) -> dict: ...
    def vault_merge(self, files: dict, exported_at: str) -> dict: ...   # 신설
    def list_runs(self, limit=20) -> list: ...
```

`SUPABASE_ANON_KEY` 가 신규 환경변수로 추가된다.

### 3.4 인증 — Supabase Auth로 교체

- 홈페이지 `/admin/` 이 이미 Supabase Auth UID 기반 RLS로 돌고 있다
  (→ [[12 홈페이지 제품 페이지와 상담 관리]]) — **검증된 패턴을 그대로 재사용**한다.
- `ui_common.require_password()` → `require_login()`. 이메일+비밀번호 로그인,
  성공 시 `st.session_state` 에 `access_token`/`refresh_token`/`tenant_id` 보관.
  만료(1시간)는 refresh 토큰으로 자동 갱신, 실패 시 재로그인.
- **가입은 열지 않는다.** 대표가 고객사 계정을 만들어 주는 초대 방식으로 시작 —
  공개 가입은 곧 비용 노출이다. (홈페이지 상담 폼 → 계정 발급이 자연스러운 동선.)
- `APP_PASSWORD` 게이트는 전환기 동안 `ALLOW_LEGACY_PASSWORD` 플래그로만 남기고
  전환 완료 후 제거한다. 인증 경로 두 벌은 그 자체가 부채다.
- 브라우저 새로고침 시 세션이 날아가는 Streamlit 한계는 초기엔 감수한다
  (쿠키 영속화는 서드파티 컴포넌트 의존 — 고객 불만이 실제로 나오면 착수).

### 3.5 비용 방어와 과금 (유료화의 실제 게이트)

조사 1건은 프로바이더 수 × (1+라운드) + 종합 + 추출까지 **수십 회 LLM 호출**이다.
인증만 붙이고 열면 원가를 모르는 채로 팔게 된다.

- **계측**: `ra_usage(tenant_id, run_id, provider, mode, in_tokens, out_tokens,
  est_cost, created_at)`. 각 SDK 응답의 usage 필드를 수집한다 —
  [[09 향후 고도화 백로그]]의 "비용 대시보드"가 여기서 함께 해소된다.
- **한도**: 플랜별 월 실행 수·토큰 상한. **실행 시작 전에 확인(fail-closed)**,
  초과 시 풀 모드를 막고 라이트 모드만 허용한다(→ [[14 라이트 모드]]가 그대로 완충재).
- **BYO 키**(고객사 자체 API 키)는 **선결 조건이 있다**: 지금 프로바이더는
  `anthropic.Anthropic()` / `OpenAI()` 처럼 키를 **env에서 암묵적으로** 읽고,
  Streamlit은 1프로세스에 여러 세션이 붙는다. 사용자별 키를 `os.environ` 에 넣으면
  **옆 사용자에게 샌다**. 따라서 BYO는 ① 프로바이더 생성자에 키 인자 주입
  ② `bridge_secrets_to_env` 를 서버 공용 키 전용으로 한정 — 이 둘을 먼저 한다.
  키 보관 자체가 보안 책임을 키우므로 **MVP는 대표 키 + 한도**, BYO는 요구가
  나오면 착수한다.
- 결제(카드·구독) 연동은 이 문서 범위 밖. 초기 5~10곳은 **수동 인보이스**가 싸다.

### 3.6 모니터링·알림의 테넌트화

- `watch_runner.run_due_watches(tenant_id, ...)` 로 시그니처 변경,
  `watch_run.py` 는 **활성 테넌트를 순회**하며 테넌트별로 호출한다.
  한 테넌트의 실패가 다른 테넌트 배치를 물들이지 않게 예외를 테넌트 단위로 가둔다
  (개별 감시 실패를 종료 코드로 올리지 않는 기존 원칙의 한 층 위).
- 알림 수신자는 전역 `NOTIFY_EMAIL_TO` 대신 **`ra_watches.notify_to`**(행별) →
  없으면 테넌트 기본 수신자. SMTP 발신 계정은 대표 것 하나를 공용으로 써도 된다.
- 감시 실행의 LLM 비용도 `ra_usage` 에 해당 테넌트로 귀속시킨다.

### 3.7 캐시와 세션 (놓치면 유출되는 곳)

- `st.cache_data` 3곳(`_list_runs_cached`, 감시 목록, 볼트)은 **캐시 키에
  `tenant_id` 를 반드시 포함**한다. 인자로 받는 형태로 바꾸면 자동으로 키에 들어간다.
  테넌트 컬럼을 다 붙여 놓고 여기서 새는 것이 다중 테넌트 전환의 전형적 사고다.
- `st.session_state` 는 브라우저 세션 단위라 안전. **`os.environ` 은 프로세스
  전역이라 위험** — 사용자별 값은 절대 넣지 않는다(3.5와 같은 뿌리).
- `@st.cache_resource` 로 프로바이더 클라이언트를 캐시하지 않는다(키가 섞인다).

### 3.8 기밀 격리의 승격

문서 13 안전장치 3(`🔒기밀후보` 마킹)은 1인용 임시 조치였다. 테넌트 분리가
들어오면 **고객사 간 격리는 DB가 보장**하고, 마킹은 테넌트 **안에서의** 취급
(비서 답변 노출 여부 등)으로 역할이 좁아진다. 지금 코드의 `include_confidential`
토글은 그대로 유효하다.

## 5. 구현 로드맵 (단계마다 독립적으로 배포 가능)

| 단계 | 내용 | 이 단계가 끝나면 |
|---|---|---|
| 1 | 테넌트 스키마 + RLS + `Store` 객체화 + 기존 데이터 마이그레이션 (화면은 그대로, 세션은 '기본' 테넌트 고정) | 데이터가 분리 가능한 형태가 됨. **사용자 체감 변화 0, 회귀 위험만 처리** |
| 2 | Supabase Auth 로그인 + 테넌트 바인딩, 캐시 키, `APP_PASSWORD` 격하 | **두 번째 고객사를 안전하게 붙일 수 있음** |
| 3 | 볼트 zip **병합·충돌·스냅샷·tenant 대조** + 테넌트별 시드 | 옵시디언 왕복이 사고를 안 내는 상태 (요구 3의 본체) |
| 4 | 사용량 계측 `ra_usage` + 플랜 한도(fail-closed) + 관리자 화면 | **유료로 팔아도 되는 상태** |
| 5 | 모니터링 테넌트화 + 행별 알림 수신자 | 고객사가 자기 알림을 자기 메일로 받음 |
| 6 | Dropbox/OneDrive 앱 폴더 자동 동기화 | zip 왕복 탈출 |
| 7 | (요구 시) GitHub 연동 · BYO 키 · 결제 연동 | — |

**1→2 순서는 뒤집지 않는다.** 로그인부터 붙이면 데이터가 섞인 채로 사용자만
늘어난다.

## 6. 위험과 안전장치

1. **교차 테넌트 유출** — 최대 리스크. RLS를 1차 방어로 두고, 추가로 테넌트 2개를
   만들어 "A 세션에서 B의 run/볼트/감시가 보이지 않는다"를 **회귀 테스트로 고정**한다.
   캐시 경로도 포함해서(3.7) 테스트한다.
2. **마이그레이션 중 볼트 소실** — `not null` 부여 전에 backfill, 실행 전
   `ra_vault`·`ra_runs` 덤프를 받아 둔다. `vault_replace_all` 을 쓰는 기존 UI는
   1단계에서 곧바로 잠근다.
3. **비용 폭주** — 한도 확인은 실행 **시작 전**, 초과 시 차단(fail-closed).
   문서 10의 불변 리스크("앱은 대표 키로 작동")가 유료화로 커진 형태다.
4. **탈퇴·해지 처리** — `on delete cascade` 로 테넌트 삭제 시 전량 삭제되지만,
   **삭제 전 볼트 zip을 내보내 인도**하는 절차를 계약과 화면 양쪽에 넣는다.
   고객 데이터는 고객 것이다.
5. **개인정보·계약** — 고객사 자료를 대표 인프라(Supabase·LLM API)에 태우는 순간
   위탁 처리 관계가 생긴다. 최소한 ① 어느 LLM에 무엇이 전송되는지 명시
   ② 학습 미사용 조항 확인 ③ 보관·파기 기준 — 세 가지는 판매 전에 문서화한다.
6. **`pages/` 추가 배포 시 Reboot 필수** — 관리자 화면을 새 페이지로 만들면
   이 함정을 다시 밟는다 (→ [[08 작업 이력]] 26번).

## 7. 검토 후 기각한 대안

- **볼트를 사용자별 폴더 접두사(`tenants/<id>/…`)로만 나누기** — 스키마 변경 없이
  당장은 되지만, 격리가 **문자열 규칙**에 걸린다. `like` 패턴 하나 잘못 쓰면
  전 고객사가 열린다. 유료 서비스에서 감당할 수 없는 종류의 실수.
- **service_role 유지 + 앱 코드 필터만** — 구현은 가장 싸다. 그러나 유출 방지가
  전적으로 "모든 호출부가 필터를 기억한다"에 달린다. 호출부가 이미 20곳이고
  기능은 계속 는다. 1번 결함과 같은 사고의 재생산.
- **Streamlit 앱을 고객사별로 복제 배포** — 격리는 완벽하지만 배포·업데이트·비용이
  고객 수만큼 곱해진다. 5곳만 넘어도 운영이 무너진다.
- **구글 드라이브 양방향을 2단계로** — restricted scope 검수·CASA 비용이 초기
  고객 규모에 안 맞는다(3.1). 규모가 커지면 Dropbox 어댑터 옆에 추가하는 형태로 재검토.
- **볼트를 앱 DB 단일 원본으로 하고 Obsidian은 읽기 전용** — 문서 13에서 이미
  기각(자동 생성 노트를 고치면 덮어써진다 = 볼트가 남의 문서가 된다). 다중 사용자가
  되어도 이 판단은 바뀌지 않는다.
