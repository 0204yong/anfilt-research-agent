# 19 두 제품 구성과 자동 업데이트

> 상태: **설계 확정 (2026-08-07) · 미착수**.
> [[18 설치형 패키지]]가 "설치판을 어떻게 만드나"라면, 이 문서는
> **"두 제품을 어떻게 함께 굴리고, 패치를 어떻게 고객 PC까지 보내나"** 이다.

## 요구 (사용자, 2026-08-07)

1. **2개 상품**으로 만든다
   - 현재의 호스팅 버전 = **영업용 무료 체험판**
   - 설치 버전 = 구매 확정 고객이 **본인 PC에 설치**해 쓰는 정식판
2. 정식판은 **ANFILT 홈페이지에서 다운로드**한다 (Steam처럼)
3. 새 패치가 나오면 **고객 PC가 자동으로 업데이트**된다

## 답: 가능하다. 그리고 새로 지을 인프라가 거의 없다

| 필요한 것 | 이미 있는 것으로 해결 |
|---|---|
| 업데이트 매니페스트 호스팅 | **홈페이지(Netlify)에 JSON 파일 하나** — 인프라 추가 0 |
| 설치 파일 호스팅 | **GitHub Releases** — 무료·CDN, 대용량 배포에 적합 |
| 릴리스 자동화 | [[11 원커맨드 배포]]에 빌드 잡 하나 추가 |
| 체험 코드 발급·관리 | 홈페이지 `/admin/` 상담 관리 화면 확장 (→ [[12 홈페이지 제품 페이지와 상담 관리]]) |
| 라이선스 저장 | 기존 Supabase에 테이블 1개 |
| 체험 볼트 → 정식판 이주 | **이미 만든 zip 내보내기/가져오기 코드** (아래 3절) |

## 1. 두 제품의 경계

|  | **체험판** (호스팅) | **정식판** (설치) |
|---|---|---|
| 어디서 도나 | Streamlit Cloud (현행) | 고객 PC |
| 접근 | 홈페이지 상담 → **체험 코드 + 링크** | 홈페이지에서 다운로드 → 라이선스 키 |
| LLM 키 | **대표 키** (원가 발생) | **고객 본인 키** (원가 0) |
| 볼트 | 서버 사본, 체험 코드별 분리, **만료 시 삭제** | 로컬 폴더 (Obsidian 원본) |
| 모드 | **라이트 모드 고정** (→ [[14 라이트 모드]]) | 전 모드 |
| 한도 | 실행 N회 · 유효기간 (fail-closed) | 없음 |
| 모니터링 | **비활성** (장기 기능이라 체험에 안 맞음) | 활성 (로컬 스케줄러) |
| 목적 | **"이게 뭔지 15분 안에 보여준다"** | 실무 도구 |

체험판의 역할은 기능 전부를 주는 게 아니라 **"조사 → 토론 → 보고서 → 볼트에 지식이
쌓인다"는 한 바퀴를 직접 만져보게 하는 것**이다. 전부 주면 살 이유가 없고,
너무 적게 주면 이 제품의 핵심(축적)이 안 보인다. 그 균형점이 위 표다.

### 체험판의 격리는 "싼 방식"으로 한다

[[17 다중 사용자와 테넌트 분리]]는 유료 SaaS 전제라 RLS·JWT까지 갔지만,
**체험판에는 그 수준이 필요 없다.** 근거:

- 체험은 기간 한정이고, 화면과 약관에 **"실제 고객사 기밀 자료는 올리지 마세요"** 를
  명시한다. 진짜 자료는 정식판(로컬)에서 다룬다 — 그게 정식판을 사는 이유이기도 하다.
- 그래서 격리는 **`trial_code` 컬럼 하나 + 조회 필터**로 충분하다.
  `ra_vault` PK를 `(trial_code, path)` 로 바꾸고, `ra_runs` 에 컬럼을 더한다.
  service_role 단일 키를 유지하고 RLS는 도입하지 않는다.
- **[[17 다중 사용자와 테넌트 분리]]가 통째로 버려지지 않는다** — 그 문서의 결함 목록과
  `Store` 객체화(테넌트 없이 볼트를 못 부르게 하는 설계)는 **여기서 축소판으로
  재사용**된다. `st.cache_data` 캐시 키 문제(17의 3.7)는 체험판에서도 **그대로
  유효한 유출 경로**이므로 반드시 함께 고친다.

> 이건 타협이 아니라 **비례**다. 지키는 대상의 값어치가 다르면 자물쇠의 값도 달라야 한다.
> 다만 "체험판에는 기밀을 올리지 않는다"는 전제가 깨지면(고객이 그냥 올려버리면)
> 근거가 무너지므로, **업로드 화면에 경고를 상시 노출**하고 만료 시 실제로 삭제한다.

### 체험 코드 발급·만료

```
홈페이지 상담 폼(leads) ──▶ /admin/ 에서 "체험 코드 발급" 버튼
                              └─▶ ra_trials 1행 + 안내 메일(코드·링크·유효기간)
```

- `ra_trials(code, email, company, expires_at, runs_used, runs_limit, created_at)`
- 앱 진입은 지금의 `APP_PASSWORD` 한 겹 대신 **체험 코드 입력**으로 바꾼다
  ([ui_common.py:39](ui_common.py:39) 게이트 자리에 그대로 들어간다).
- 만료·한도 초과 시: 화면을 잠그고 **"정식판 구매하기" CTA + 볼트 내보내기 버튼**만 남긴다.
  마지막에 보여줄 화면은 광고가 아니라 **"당신이 만든 지식을 가져가는 버튼"** 이다.
- 만료 30일 뒤 해당 코드의 볼트·조사 이력을 **자동 삭제** (배치 또는 앱 시작 시 정리).

## 2. 하나의 코드베이스, 두 개의 빌드

두 제품이 서서히 갈라지면 유지가 무너진다. 분기를 화면 곳곳에 뿌리지 않고
**경계 세 개로 모은다.**

```
core/edition.py          EDITION = "trial" | "installed"  + 기능 플래그
core/store.py            같은 인터페이스, 구현 2종
   ├─ SupabaseStore(trial_code)      체험판
   └─ LocalStore(vault_path)         정식판   (→ 18 문서 5절)
core/keys.py             키 출처: 서버 Secrets  vs  OS 키체인
```

| 갈리는 지점 | 체험판 | 정식판 |
|---|---|---|
| 저장소 | `SupabaseStore` | `LocalStore` |
| 키 | `os.environ` (서버 공용) | `keyring` (사용자 등록) |
| 진입 | 체험 코드 게이트 | 라이선스 확인 |
| 한도 | 실행 수·만료 검사 | 없음 |
| 볼트 UI | zip **내보내기**(이주용) | 폴더 열기·전환 |
| 모니터링 페이지 | 숨김 | 표시 |

`app.py`·`pages/*` 는 `edition.can("monitoring")` 같은 **플래그만 묻는다.**
화면 코드에 `if EDITION == "trial"` 이 흩어지기 시작하면 그때부터 두 제품이 갈라진다.

`pipeline`·`librarian`·`ontology`·`vault_render`·`reports` 는 **양쪽에서 완전히 동일**하다.
체험판과 정식판이 **같은 엔진**이라는 것이 영업에서 중요하다 — 체험에서 본 품질이
그대로 온다.

## 3. 체험 → 구매 → 설치의 이음매 (설계의 심장)

여기가 깨지면 두 제품 전략 전체가 무의미해진다. **체험에서 쌓은 지식을 잃으면
고객은 "처음부터 다시"를 시작해야 하고, 그게 구매를 막는다.**

```
[체험판]  조사 3~5건 실행 → 볼트에 엔티티가 쌓임
            │
            │  "내 지식볼트 가져가기" (만료 화면에도 상시 노출)
            ▼
        지식볼트_2026-09-01.zip   (엔티티 + 조사 노트 + run.json)
            │
            ▼
[정식판]  최초 실행 마법사 ③단계: "체험판 볼트 가져오기"
            → 폴더에 풀고 · 조사 이력은 sqlite로 적재 · 인덱스 재생성
            ▼
        Obsidian에서 열기 — 체험 때 쌓은 노트가 그대로 있다
```

**[[18 설치형 패키지]]에서 "불필요해진다"고 한 zip 왕복 코드가 여기서 되살아난다.**
역할이 바뀔 뿐이다 — **상시 동기화 수단(폐기)** → **1회성 이주 도구(유지)**.
그것도 이미 만들어 둔 것들이 그대로 쓰인다:

- `build_full_vault_zip` (엔티티·조사 노트·run.json 포함)
- `parse_vault_zip` — 최상위 폴더 방어·볼트 아님 거부 (2026-08-04 견고화분)
- `ontology.build_index` — 이주 후 인덱스 재생성

즉 **이주 경로 구현 비용이 거의 0**이다. 마법사에 단계 하나 붙이는 일이다.

## 4. 자동 업데이트 — "Steam처럼"

### 4.1 전체 그림

```
개발 PC ── git tag v1.4.2 ──▶ GitHub Actions
                                 ├─▶ 설치판 빌드 (인스톨러 + 델타 zip + sha256)
                                 ├─▶ GitHub Releases 업로드      ← 파일 호스트
                                 └─▶ 홈페이지 repo에 latest.json 커밋
                                        └─▶ Netlify 배포 (즉시)
                                              ▲
고객 PC ── 앱 시작 시 latest.json 확인 ────────┘
             │ 새 버전 있음
             ▼
        델타 다운로드 → sha256 검증 → 앱 종료 → 교체 → 재시작
             (실패 시 이전 버전 폴더로 롤백)
```

### 4.2 매니페스트 — 홈페이지에 JSON 파일 하나

`https://anfilt-homepage.netlify.app/releases/latest.json`

```json
{
  "version": "1.4.2",
  "released": "2026-09-01",
  "runtime_version": "1.0",
  "min_supported": "1.2.0",
  "notes_url": "https://anfilt.../releases/1.4.2",
  "critical": false,
  "delta":     {"url": "https://github.com/.../app-1.4.2.zip", "sha256": "…", "size": 4812345},
  "installer": {"url": "https://github.com/.../ResearchAgent-Setup-1.4.2.exe", "sha256": "…", "size": 268435456}
}
```

- 홈페이지는 Netlify **정적 호스팅**이라 파일 하나 추가로 끝난다. 서버·API 불필요.
- 정식판 다운로드 페이지도 이 JSON을 읽어 **항상 최신 버전을 가리키게** 한다
  (버전이 하드코딩된 링크가 낡는 사고를 없앤다).

### 4.3 파일은 GitHub Releases에

- 인스톨러는 200~400MB다. **Netlify에 두지 않는다** (대역폭·파일 크기 제약).
- GitHub Releases는 무료에 CDN이고 대용량 배포에 적합하다.
- ⚠️ 앱 저장소가 private이면 릴리스 에셋도 인증이 필요하다 →
  **배포 전용 public 저장소**(`anfilt-research-agent-releases`)를 따로 두고
  **빌드 산출물만** 올린다. 소스는 올리지 않는다.

### 4.4 무엇을 받게 할 것인가 — 델타 우선

Steam 같은 파일 단위 델타까지는 필요 없다. 두 갈래면 충분하다.

| 상황 | 받는 것 | 크기 |
|---|---|---|
| 앱 코드·시드·프롬프트만 바뀜 (**대부분의 패치**) | `app-<버전>.zip` — `.py`·시드·정적 자산만 | **수 MB** |
| 파이썬 런타임/의존성이 바뀜 (`runtime_version` 상이) | 전체 인스톨러 재설치 (`/VERYSILENT`) | 수백 MB |

매니페스트의 `runtime_version` 을 클라이언트가 가진 값과 비교해 자동으로 고른다.
실제 체감은 "대부분의 패치는 몇 초, 가끔 큰 업데이트" — 원하던 그림이다.

### 4.5 교체 절차 (함정이 있는 곳)

**실행 중인 앱이 자기 소스를 갈아치우면 안 된다.** import된 모듈을 중간에 바꾸면
상태가 꼬인다. 그래서 교체는 **별도 업데이터 프로세스**가 한다.

```
1. 다운로드 → sha256 검증 (불일치면 중단, 사용자에게 알림)
2. app/ 폴더를 app.bak/ 로 이름 변경        ← 롤백 지점
3. 앱 종료 → 업데이터가 새 app/ 을 풀기
4. 앱 재시작 → 시작 자가진단 통과 시 app.bak/ 삭제
5. 어느 단계든 실패하면 app.bak/ 을 되돌리고 이전 버전으로 재시작
```

- **볼트와 `.research-agent/` 는 프로그램 폴더 바깥**에 있으므로 업데이트가 사용자
  데이터를 절대 건드리지 않는다 ([[18 설치형 패키지]] 8절의 분리가 여기서 값을 한다).
- **DB 스키마 마이그레이션**: `.research-agent/agent.db` 에 `schema_version` 을 두고
  시작 시 순차 적용. 볼트 마크다운 포맷은 **파괴적 변경 금지**(사용자 큐레이션 존중 —
  `merge_entity` 원칙과 같은 뿌리).
- **강제 업데이트**(`min_supported`): 프롬프트 스키마나 모델 ID가 바뀌어 옛 버전이
  오작동하게 되면 잠근다. 가상의 걱정이 아니다 — 이 프로젝트는 이미
  `gemini-2.5-flash` 가 신규 사용자에게 404를 내는 일을 겪었고
  ([config.py:53](core/config.py:53)), 그때 **낡은 클라이언트는 조용히 고장 난다.**
- **오프라인**: 매니페스트 조회 실패는 조용히 넘어간다. 업데이트 확인 실패가 앱을
  막으면 안 된다.
- **자동/수동**: 기본은 "자동 다운로드 + 재시작 시 적용", 설정에서 "확인만" 으로 변경 가능.
  조사 실행 중에는 절대 재시작하지 않는다 (20분짜리 작업이 날아간다).

### 4.6 라이선스는 다운로드가 아니라 실행에 건다

- 매니페스트도 설치 파일도 **공개**로 둔다. 다운로드를 막으려 들면 인프라만 복잡해지고
  어차피 뚫린다. **막아야 할 것은 다운로드가 아니라 실행이다.**
- 실행 통제의 상세 설계는 → **[[20 라이선스와 복제 방지]]**.
  요약: 라이선스를 "실행 허가"가 아니라 **프롬프트 팩의 인출 권한**으로 만들어,
  라이선스 없는 복제본이 **동작할 부품 자체를 갖지 못하게** 한다.
- **서명 인증서**(연 20~40만원)는 매출이 나면 우선 투자한다. 자동 업데이트의 신뢰도와
  백신 오탐([[18 설치형 패키지]] 2절) 을 동시에 해결하는 유일한 항목이다.
- 업데이트와 라이선스가 만나는 지점: **팩 버전을 릴리스마다 회전**시키면
  자동 업데이트가 곧 복제 방어 수단이 된다 ([[20 라이선스와 복제 방지]] L3).

## 5. 릴리스 파이프라인 — [[11 원커맨드 배포]]의 확장

지금의 "배포해줘"는 **두 저장소 push**였다. 여기에 **태그 릴리스**가 하나 붙는다.

```
"배포해줘"          → 홈페이지 + 체험판(Streamlit Cloud)  [지금 그대로]
"릴리스해줘 1.4.2"  → 태그 push → Actions 빌드 → Releases 업로드
                      → 홈페이지 latest.json 커밋 → Netlify 배포
```

- 체험판과 정식판의 **버전을 항상 같이 올린다.** 영업 자리에서 체험판이 보여준
  기능이 정식판에 없으면 신뢰를 잃는다.
- 화면 하단에 버전을 표시한다(양쪽 모두). 지원 문의에서 제일 먼저 필요한 정보다.
- 릴리스 전 체크리스트: 시크릿 스캔(기존 절차) · 깨끗한 Windows에서 **설치→실행→조사
  1건** · **이전 버전에서 자동 업데이트** 실측 (신규 설치만 테스트하면 업데이트 경로가
  안 잡힌다).

## 6. 로드맵

[[18 설치형 패키지]]의 로드맵에 이 문서의 항목을 끼운 통합 순서다.

| 단계 | 내용 | 산출 |
|---|---|---|
| 0 | **패키징 스파이크 1주** (→ 18 문서 6절) | 배포 형태 확정 |
| 1 | `edition.py` + `store.py` 인터페이스 분리 (`SupabaseStore`/`LocalStore`) **+ 프롬프트 팩 분리**(→ [[20 라이선스와 복제 방지]] — 나중에 하면 전 모듈을 다시 헤집는다) | 한 코드베이스 두 빌드의 뼈대 |
| 2 | **체험판 개조** — 체험 코드 게이트·`trial_code` 분리·캐시 키·한도·모니터링 숨김 | **영업에 바로 투입 가능** |
| 3 | 정식판 로컬화 + 설정 화면(키체인) + 최초 실행 마법사 | 내 PC에서 도는 정식판 |
| 4 | **이주 경로** — 체험 볼트 zip 가져오기 (3절) | 체험→구매 이음매 완성 |
| 5 | 런처 + 인스톨러 + 홈페이지 다운로드 페이지 | 남에게 건넬 수 있는 물건 |
| 6 | **자동 업데이트** (매니페스트·델타·업데이터·롤백) | 패치가 고객 PC까지 간다 |
| 7 | 라이선스 활성화(팩 인출·서명·기기 바인딩) + `/admin/` 발급·기기 해제 화면 → [[20 라이선스와 복제 방지]] | **판매 가능 상태** |
| 8 | 로컬 스케줄러(모니터링) · macOS · 팀 공유판 | — |

**2단계를 먼저 놓는 이유**: 체험판 개조는 작업량이 적고(현행 앱 + 코드 게이트 + 한도),
끝나는 즉시 **영업을 시작할 수 있다**. 정식판을 다 만든 뒤에 영업을 시작하면
검증 없이 몇 달을 쓰는 셈이 된다. 체험판으로 받은 반응이 3~7단계의 우선순위를 정한다.

## 7. 이 구조의 약한 곳

정직하게 셋이다.

1. **체험판 원가는 여전히 대표 부담이다.** 라이트 모드 고정 + 실행 한도 + 만료로
   묶지만, 영업이 잘될수록 비용이 는다. 체험 코드당 예상 원가를 **실측해 단가를 잡아
   두고**, 월 총 실행 수 상한(전역 킬 스위치)을 둔다.
2. **업데이트가 고장 나면 조용하다.** 자동 업데이트는 성공할 때 안 보이고 실패할 때도
   잘 안 보인다. 앱 화면에 **현재 버전과 마지막 확인 시각을 상시 표시**하고,
   업데이트 실패는 로그가 아니라 **화면 배너**로 올린다.
3. **두 제품이 갈라진다.** 시간이 지나면 체험판에만 있는 임시 조치, 정식판에만 있는
   기능이 쌓인다. 2절의 경계 셋(`edition`·`store`·`keys`)을 **넘는 분기는 리뷰에서
   막는다**는 규칙을 지금 정해 둔다.

## 8. 결정 대기 항목

| 항목 | 필요한 판단 |
|---|---|
| 체험 기간·실행 횟수 | 예: 14일 / 라이트 5회. 원가 실측 후 확정 |
| 체험판에 지식 비서를 열지 | 축적의 가치를 보여주는 최고의 화면이지만 호출이 는다 |
| 정식판 가격 형태 | 영구 + 유지보수 갱신 vs 연간 (업데이트 권한과 직결) |
| 좌석 정책 | 1 라이선스 = 1 PC인지, 개인당 N대 허용인지 |
| 코드 서명 인증서 | 구매 시점 — 오탐·업데이트 신뢰도에 직결 |
