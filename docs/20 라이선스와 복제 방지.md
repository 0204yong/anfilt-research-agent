# 20 라이선스와 복제 방지

> 상태: **설계 확정 (2026-08-07) · 미착수**.
> [[18 설치형 패키지]] 8절의 "복제 방어는 포기한다"는 방침을 **철회하고 대체**한다
> (사용자 지시, 2026-08-07). [[19 두 제품 구성과 자동 업데이트]] 4.6절의 라이선스
> 항목도 이 문서로 확장된다.

## 요구 (사용자, 2026-08-07)

> "구매자 외에는 다른 사람이 공짜로 사용하는 게 **불가능**하게 만들어야 한다."

## 먼저: 이 제품에서 흔한 방식이 왜 안 통하는가

설치판은 **파이썬 소스가 그대로 담긴다**. `if not license_ok: return` 을 메모장으로
지우면 끝난다. 컴파일 언어보다 훨씬 쉽다. 즉 **클라이언트 안에서만 판정하는 라이선스는
이 제품에서 사실상 없는 것과 같다.**

그래서 방향을 바꾼다.

> **라이선스를 "실행 허가"가 아니라 "필수 부품의 인출 권한"으로 만든다.**
> 검사를 지우는 것으로는 아무것도 얻지 못하게 한다 — 지울 검사가 없고, 대신
> **없으면 동작할 수 없는 부품**이 비어 있기 때문이다.

## 핵심 구조 — 프롬프트 팩

이 제품의 값어치는 파이썬 코드가 아니라 **프롬프트에 있다.** 조사·토론·채점·종합
프롬프트, `REPORT_SCHEMA`, 분량 계획, 채점 기준 9종, 온톨로지 추출 스키마와 술어
12종, 지식 비서 규칙, 감시 요약 프롬프트, 그리고 ESG 시드 온톨로지 35노트 —
[[02 파이프라인 설계]]·[[13 지식 볼트와 온톨로지]]에 쌓인 설계 전부다.

이걸 **패키지에서 빼고, 라이선스로 서버에서 인출**한다.

```
설치 직후의 프로그램 = 빈 껍데기
     │  라이선스 키 + 기기 지문
     ▼
[활성화 서버]  키 유효? 좌석 남았나? 정지된 키 아닌가?
     │  서명된 프롬프트 팩 (유효기간 30일)
     ▼
로컬 캐시 (암호화 · 기기 지문에 묶임)  →  파이프라인이 비로소 구성됨
```

- 복제본을 아무리 뿌려도 **팩이 없으면 조사가 시작조차 안 된다.** 스텁을 넣어
  흉내 내려면 이 프로젝트가 1년간 쌓은 프롬프트를 처음부터 다시 만들어야 한다.
- 팩에는 **Ed25519 서명**을 붙이고 공개키를 클라이언트에 심는다. 위조 팩을 넣는
  우회를 막는다(서명 검증은 지울 수 있지만, 지워도 **진짜 팩이 없으면 소용없다** —
  이 점이 일반 라이선스 체크와 결정적으로 다르다).
- 캐시는 디스크에 암호화 저장하고 키를 **OS 키체인 + 기기 지문**에서 파생한다.
  **설치 폴더를 통째로 복사해 다른 PC에 붙여도 열리지 않는다.**
- 팩은 **릴리스마다 버전이 바뀐다.** 어렵게 한 번 추출해도 다음 패치면 낡는다.
  크랙의 유효기간이 릴리스 주기로 줄어든다.

### 개인정보·기밀 원칙은 그대로다

**서버로 가는 것은 라이선스 키와 기기 지문 해시뿐이고, 받아 오는 것은 우리 자산인
프롬프트다.** 고객사 자료·조사 주제·볼트 내용은 **일절 전송되지 않는다.**
[[18 설치형 패키지]]의 최대 판매 포인트("고객사 자료가 저희 서버를 거치지 않습니다")는
훼손되지 않는다 — 이 구분을 계약서와 제품 화면 양쪽에 명시한다.

## 방어 계층 (효과를 정직하게 표시)

| 층 | 내용 | 실제 효과 |
|---|---|---|
| **L0** 소스 보호 | `.py` → 바이트코드 배포, 문자열 난독화 | **낮음.** 그래도 "메모장으로 한 줄 지우기"는 막는다. 비용도 낮아 넣는다 |
| **L1** 라이선스 키 + 기기 바인딩 | 키 발급, 좌석 수, 기기 등록/해제 | **정직한 다수를 100% 막는다.** 실제 위협의 대부분 |
| **L2** **프롬프트 팩 인출** | 위 구조 | **높음 — 아키텍처 방어.** 복제본을 무력한 껍데기로 만든다 |
| **L3** 팩 회전 + 강제 업데이트 | 릴리스마다 팩 버전 교체, `min_supported` 미만 잠금 | **높음.** 크랙의 수명을 릴리스 주기로 제한 |
| **L4** 이상 활성화 탐지 | 한 키가 다수 기기·원격지에서 활성화 → 자동 경고·키 정지 | 중간. 유출된 키를 조기에 끊는다 |
| **L5** 계약·법적 | 라이선스 약관, 기업 고객 감사 조항 | **B2B에서는 의외로 강력하다** (아래) |

### 실제 위협 모델

이 제품의 고객은 **기업 ESG 실무 조직**이다. 조직은 크랙 소프트웨어를 사내에 들이지
않는다 — 감사·조달·법무 리스크가 소프트웨어 값보다 훨씬 크기 때문이다.
현실적인 위협은 조직적 불법 유통이 아니라 **"옆 팀에 복사해 주기"** 이고,
**L1 + L2 조합이 그것을 완전히 차단한다.**

## 활성화 서버 — 유일하게 새로 짓는 것

**Supabase Edge Function** 하나면 된다(기존 프로젝트에 얹는다, 무료 티어).
라이선스 상태가 Supabase에 있으므로 한 홉으로 끝난다.
(대안: 홈페이지가 이미 Netlify에 있으니 Netlify Functions도 가능. 다만 라이선스
조회를 위해 Supabase로 한 번 더 나가야 한다.)

```
POST /activate    {license_key, device_fp, app_version}
   → 200 {pack, pack_version, signature, expires_at, seat_no}
   → 403 {reason: "invalid" | "expired" | "seats_full" | "revoked"}

POST /refresh     {license_key, device_fp}       ← 만료 전 자동 갱신
POST /deactivate  {license_key, device_fp}       ← PC 교체 시 좌석 반납
```

```sql
create table public.ra_licenses (
  license_key text primary key,          -- 발급 시 생성 (예: ANF-XXXX-XXXX-XXXX)
  email       text not null,
  company     text,
  seats       int  not null default 1,
  status      text not null default 'active',   -- active|suspended|revoked
  expires_at  timestamptz,               -- 연간 라이선스면 만료일
  created_at  timestamptz not null default now()
);

create table public.ra_activations (
  license_key   text not null references public.ra_licenses(license_key) on delete cascade,
  device_fp     text not null,           -- 해시. 원본 식별자는 저장하지 않는다
  device_label  text default '',         -- 사용자가 알아볼 이름 (해제 화면용)
  first_seen_at timestamptz not null default now(),
  last_seen_at  timestamptz not null default now(),
  app_version   text default '',
  primary key (license_key, device_fp)
);
```

- **기기 지문**은 Windows Machine GUID + 볼륨 시리얼을 **해시**한 값이다.
  원본이나 개인 식별 정보는 저장하지 않는다.
- 발급은 `/admin/` 에 체험 코드 발급 옆에 붙인다 (→ [[12 홈페이지 제품 페이지와 상담 관리]]).
- **기기 해제(좌석 반납)는 반드시 셀프서비스로 만든다.** 없으면 PC 교체·재설치
  때마다 문의가 오고, 그게 지원 부담의 1위가 된다.

## 오프라인·장애 시 동작 (여기서 신뢰가 갈린다)

강하게 잠그되, **정당한 구매자가 못 쓰는 일은 절대 없어야 한다.**

| 상황 | 동작 |
|---|---|
| 인터넷 일시 단절 | 캐시된 팩으로 **정상 동작** (유효기간 30일 안) |
| 갱신 실패 지속 | 만료 7일 전부터 배너 경고 → 만료 시 **조사만 잠금** |
| 활성화 서버 장애 | 클라이언트가 실패를 **유예로 처리**. 우리 장애로 고객이 멈추면 안 된다 |
| 라이선스 만료·해지 | 다음 갱신 시점에 잠금 (최대 유예기간만큼 지연 — 감수한다) |
| 폐쇄망 고객 | **오프라인 활성화 파일** 발급 (기기 지문 제출 → 기기 전용 서명 팩). 수동 절차 |

**잠겨도 볼트 열람·내보내기·과거 보고서 다운로드는 계속 허용한다.**
고객 데이터를 인질로 잡지 않는다 — 이건 방침이자 분쟁 예방책이다.

## 체험판과의 관계

체험판은 **호스팅**이라 복제 위험이 없다. 체험 코드·실행 한도·만료로 이미
통제된다(→ [[19 두 제품 구성과 자동 업데이트]] 1절). 프롬프트 팩도 서버 안에 있으니
그대로 쓴다. 즉 **이 문서의 장치는 전부 설치판에만 적용**된다.

| 빌드 스크립트 | 바이트코드 배포, **팩을 패키지에서 제외** |

> 상수로 흩어져 있다. 다만 이건 라이선스와 무관하게도 값이 있다 —
> 프롬프트를 **앱 재배포 없이 갱신**할 수 있게 되어, ESG 규제 변화(CSRD·ESRS·K-ESG)에
> 프롬프트만 바꿔 대응할 수 있다.

## 로드맵에서의 위치

[[19 두 제품 구성과 자동 업데이트]] 6절 로드맵의 **7단계(라이선스)를 확장**한다.
다만 **프롬프트 팩 분리(1단계 작업)는 앞당긴다** — 나중에 하면 전 모듈을 다시 헤집어야 한다.

| 조정 | 내용 |
|---|---|
| 1단계에 추가 | `core/prompts/` 팩 분리 (로컬 파일에서 읽는 형태로 먼저) |
| 7단계 | 활성화 서버 + 서명 + 암호화 캐시 + 기기 관리 화면 |
| 상시 | 릴리스마다 팩 버전 회전 (L3) |

## 남는 한계 (숨기지 않는다)

숙련된 공격자가 **유효한 라이선스로 한 번 활성화한 뒤 메모리에서 팩을 덤프**하는
것은 막을 수 없다. 어떤 상용 DRM도 이 지점은 못 막는다. 다만 그 경우에도:

- **유효한 라이선스를 사야** 그 한 번이 가능하다 (돈을 내고 시작해야 한다)
- 추출한 팩은 **다음 릴리스에 낡는다** (L3)
- 그 노력의 대상은 기업 실무자가 아니다 — **우리 고객층의 위협이 아니다**

"불가능"에 실무적으로 가장 가까운 지점이 여기다. 그 이상은 비용만 늘고
정당한 고객의 사용성만 해친다.

## 결정 대기 항목

| 항목 | 판단 |
|---|---|
| 팩 유효기간 | 30일 권장 (짧을수록 강하지만 오프라인 고객이 불편) |
| 좌석 정책 | 1키=1PC vs 1키=개인 2대(노트북+데스크톱) |
| 라이선스 형태 | 영구+연 유지보수 vs 연간 구독 (만료 처리가 달라진다) |
| 폐쇄망 대응 | 오프라인 활성화를 정식 지원할지, 기업 문의 시 개별 대응할지 |
| 코드 서명 인증서 | 구매 시점 — L0·자동 업데이트 신뢰도와 직결 |
